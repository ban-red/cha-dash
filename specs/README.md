# Bundled Tier 1 specs

Each `<id>.yaml` here is a Tier 1 integration: a YAML spec the engine in [`internal/spec`](../internal/spec) runs, embedded and registered at init by this package. The format (`chadash/v1alpha1`) is internal and unstable until v1.0; it's documented in [`internal/README.md`](../internal/README.md#integrations) ("Tier 1 specs"), and [`seerr.yaml`](seerr.yaml) is the annotated sample.

Every spec publishes one resource, `<id>:<instance id>/app`, kind `app`, named after the instance, state `running`, with `attrs.type` = the spec's ID, a link to the configured URL, and `integration:<instance id> monitors` it. Its metrics are series on that resource. Seerr also publishes its pending requests (a fan-out resource) and has actions; a spec may define both from v0.2 (internal/README.md, "Spec actions"). All fixtures under `testdata/<id>/` are **synthetic**, written from the upstream's API docs or source; each folder's README says which.

The engine adds the shared behaviour: a 401 or 403 is an auth Repair on the secret, a 404 or 410 is an `api_changed` Repair naming the detected version, unless one of the spec's repairs already holds on what was read before the 404 (that's how an old release without an endpoint gets `unsupported_version`). Secrets in query strings (Tautulli, SABnzbd) are allowed, and never appear in errors or logs.

## Notes per spec

**Seerr.** Also Overseerr and Jellyseerr (the manifest lists them as `aliases`). Seerr is their merged successor, and `/api/v1/status` and `/api/v1/request/count` are the same in all three, so there's one spec and one ID, `seerr`, rather than three copies; Overseerr 1.x, Jellyseerr 1.x and 2.x, and Seerr pass the version check. The Homepage importer maps its `overseerr` and `jellyseerr` widgets to it.
- **Pending requests** are resources `seerr:<instance>/request/<id>`, kind `media_request`, `part_of` the app, state `pending`, with `media_type`, `requested_by` and `requested_at`: the 20 oldest, from an optional list request. Seerr's list has no titles (its UI asks TMDB for them), so a request is named by type, number and who asked ("Movie request #42 by …").
- **Actions:** `seerr.request.approve` (T1) and `seerr.request.decline` (T2: Seerr notifies whoever asked, and Cha Dash can't take it back). Both read `GET /api/v1/request/{id}` first: a request that isn't pending (status 1) is refused with a sentence ("already approved", "was declined", "isn't waiting for approval any more"), and ⌘K doesn't list them. They post `/api/v1/request/{id}/approve` or `/decline` and verify through the same read (2 or 5 for approve, 3 for decline). The API key is an administrator's, so there's no separate control credential.

**Tautulli.** Polls every 30 s: it's the "what's playing" tile. `streams` is `stream_count` (a string in Tautulli's answer), `streams.transcode` is `stream_count_transcode`, and `bandwidth.mbps` is `total_bandwidth` (kbps) in Mb/s. `streams` uses Plex's scale from the Demo Home (0–10, band 0–3). Health is `attention` when `server_status` says Tautulli has lost Plex; that request is optional, so a Tautulli without it still reads. Capability `media.sessions`, like the Demo Home's Tautulli.

**Bazarr.** `missing.episodes` and `missing.movies` are the Demo Home's keys: Bazarr's sidebar badges, the subtitles still wanted, summed over episodes and movies. `wanted` is their sum, the key the *arr tile reads. Health is `attention` with health issues (System → Status) or throttled providers, the reason naming which. Capability `media.library`, like the Demo Home's Bazarr.

**Mealie.** Reads the token's household (Mealie 2.0 and later count per household). `recipes` is a series; `recipes`, `categories` and `tags` are also attrs, as in the Demo Home. Polls every 5 minutes. On a 1.x server `/api/households/statistics` is a 404, and the repair turns it into "Mealie v1.12.0 is older than this spec supports".

**Linkding.** Counts the token's user's bookmarks: `bookmarks` is unarchived plus archived (Karakeep's count includes archived ones too), with `archived` and `tags` as attrs. Lists are paginated, so each request asks for one result and reads `count`. The Demo Home has no Linkding series (it's only checked there); `bookmarks` is Karakeep's key. Polls every 5 minutes.

**Karakeep.** `bookmarks` is the key's user's `numBookmarks` (the Demo Home's key and scale). `/api/version` is optional because older releases don't have it; without it the version is unknown and the unsupported-version repair can't fire, so a pre-0.23 server shows `api_changed` instead. Polls every 5 minutes.

**SABnzbd.** The Usenet side of the Download queue tile, beside qBittorrent; capability `downloads.queue`. Polls every 30 s, like qBittorrent. `url` includes SABnzbd's URL base (`/sabnzbd` by default; SABnzbd 3+ also answers at the root). `limit=1` reads the queue's totals without its jobs: job names can be personal, and the tile shows totals.
- `dl.mbps` is `kbpersec` (KiB/s, a string) in Mb/s to 0.1, qBittorrent's key and scale (0–1000, band 0–60).
- `queue` is `noofslots_total`, the jobs in the queue (the *arr tiles' key).
- `left.gib` is `mbleft` (MiB) in GiB to 0.1 (not in the Demo Home).
- **Paused:** the state is `paused` (else `running`) and `attrs.paused` is `true`; health stays `ok`, because a pause is usually the owner's. The Workbench draws that as "off, expected".
- `attrs.speedlimit_pct` is the speed limit as a percentage of the line speed, left out without one; `attrs.disk_free_gib` is the free space on the download folder (`diskspace1`).
- A wrong key is a 403 on recent releases (an auth Repair from the engine) and an error inside a 200 on older ones (the spec's own `auth` repair). Use the API key, not the NZB key: the NZB key can only add jobs.

**Paperless-ngx.** The documents library; capability `documents.library` (new). Polls every 5 minutes. `documents` is `documents_total` and `inbox` is `documents_inbox`, both new keys; the inbox is unknown, not 0, when no tag is marked as an inbox tag. Health is `attention` with "N documents are waiting in the inbox" from `inbox_warn` (default 50) up. The recipe makes a user with view permissions only, so the token can't change anything; Paperless-ngx counts only the documents that user may view, and `/api/status/` (the version) is staff only, so with that user the version is unknown. Spec rather than Go: one header token and two fixed GETs.

**Speedtest Tracker.** The latest result of the v1 API; capability `net.speedtest` (new). Polls every 5 minutes, since tests run hourly or so. `dl.mbps` and `ul.mbps` are `download_bits` and `upload_bits` in Mb/s to 0.1 (`dl.mbps` is qBittorrent's key, on another scale: 0–10000, band 100–1000); `ping.ms`, `jitter.ms` (Ookla's) and `packet_loss.pct` are new keys. Health is `attention` when the last test failed (its numbers are then unknown, not 0) or Speedtest Tracker marked it below the owner's thresholds (`healthy: false`), and `unknown` with "No speed test has finished yet" before the first. `/api/v1/results/latest` answers 404 until then, so it's optional, and the paged list goes first to check the token and count the results. The recipe's token has only the `results:read` ability. Spec rather than Go: one bearer token and two fixed GETs. The list's `page[size]` parameter and the 404 before the first test are from the source, not a live run.

## Limits

- Grants aren't read back for specs (deferred; see `internal/README.md`). Most of these upstreams offer no read-only key, so their credentials can change things even though Cha Dash only reads. The exceptions are Paperless-ngx (a view-only user) and Speedtest Tracker (a `results:read` token).
- Counts are per user or household where the upstream scopes them so (Mealie, Linkding, Karakeep): an instance shows what its credential's owner sees.
