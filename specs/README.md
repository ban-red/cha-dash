# Bundled Tier 1 specs

Each `<id>.yaml` here is a Tier 1 integration: a YAML spec the engine in [`internal/spec`](../internal/spec) runs, embedded and registered at init by this package. The format is `chadash/v1beta1` (v0.5), public since v0.3 ([ADR-0025](../docs/adr/0025-spec-format-public-as-v1alpha1.md)): [docs/specs.md](../docs/specs.md) is the author's guide, [`internal/README.md`](../internal/README.md#integrations) ("Tier 1 specs") has every key and what `v1beta1` changed, and [`seerr.yaml`](seerr.yaml) is the annotated sample. Every spec here was migrated from `v1alpha1` with `chadash spec migrate`, and the specs that judge dates against the clock are tested at the moment their fixtures were written for (`now:` in `fixtures.yaml`, the harness clock in their tests) instead of moving the dates to today. `chadash spec lint` and `chadash spec test` check a spec without a hub, and `chadash spec new` starts one; [`testdata/linkding/fixtures.yaml`](testdata/linkding/fixtures.yaml) shows how a fixtures folder answers `spec test`.

Every spec publishes one resource, `<id>:<instance id>/app`, kind `app`, named after the instance, state `running`, with `attrs.type` = the spec's ID, a link to the configured URL, and `integration:<instance id> monitors` it. Its metrics are series on that resource. Seerr also publishes its pending requests (a fan-out resource) and has actions; a spec may define both from v0.2 (internal/README.md, "Spec actions"). All fixtures under `testdata/<id>/` are **synthetic**, written from the upstream's API docs or source; each folder's README says which.

The engine adds the shared behaviour: a 401 or 403 is an auth Repair on the secret, a 404 or 410 is an `api_changed` Repair naming the detected version, unless one of the spec's repairs already holds on what was read before the 404 (that's how an old release without an endpoint gets `unsupported_version`). A 404 counts as `api_changed` only when the app is known to be there: an earlier request answered, or the 404 is JSON. Otherwise it's `unreachable`, since the usual cause is a reverse proxy whose backend is down. Secrets in query strings (Tautulli, SABnzbd) are allowed, and never appear in errors or logs.

The v0.5 specs (Tailscale onwards) were written from each project's API docs or source for a named version, not from a running instance: the maintainer's lab has none of them. Each recipe names the version. A backup tool's `backup.covers` is the paths it backs up on `host` (the URL's host unless set), after `path_map` (`/userdata:/mnt/user`) turns a container's paths into the host's.

The config shapes are the Homepage importer's ([07 · v0.1](../docs/plan/07-v0.1.md#instance-config-keys)): `url`, `tls` and one secret.

## Notes per spec

**Seerr.** Also Overseerr and Jellyseerr (the manifest lists them as `aliases`). Seerr is their merged successor, and `/api/v1/status` and `/api/v1/request/count` are the same in all three, so there's one spec and one ID, `seerr`, rather than three copies; Overseerr 1.x, Jellyseerr 1.x and 2.x, and Seerr pass the version check. The Homepage importer maps its `overseerr` and `jellyseerr` widgets to it.
- **Pending requests** are resources `seerr:<instance>/request/<id>`, kind `media_request`, `part_of` the app, state `pending`, with `media_type`, `requested_by` and `requested_at`: the 20 oldest, from an optional list request. Seerr's list has no titles (its UI asks TMDB for them), so a request is named by type, number and who asked ("Movie request #42 by …").
- **Actions:** `seerr.request.approve` (T1) and `seerr.request.decline` (T2: Seerr notifies whoever asked, and Cha Dash can't take it back). Both read `GET /api/v1/request/{id}` first: a request that isn't pending (status 1) is refused with a sentence ("already approved", "was declined", "isn't waiting for approval any more"), and ⌘K doesn't list them. They post `/api/v1/request/{id}/approve` or `/decline` and verify through the same read (2 or 5 for approve, 3 for decline). The API key is an administrator's, so there's no separate control credential.
- **`attrs.uses`** names its Sonarr and Radarr servers and its media server (Plex or Jellyfin) by address, from the optional `/api/v1/settings/sonarr`, `…/radarr`, `…/plex` and `…/jellyfin`. Only the address fields are extracted, never the API keys beside them.

**Tautulli.** Polls every 30 s: it's the "what's playing" tile. `streams` is `stream_count` (a string in Tautulli's answer), `streams.transcode` is `stream_count_transcode`, and `bandwidth.mbps` is `total_bandwidth` (kbps) in Mb/s. `streams` uses Plex's scale from the Demo Home (0–10, band 0–3). Health is `attention` when `server_status` says Tautulli has lost Plex; that request is optional, so a Tautulli without it still reads. Capability `media.sessions`, like the Demo Home's Tautulli. `attrs.uses` names its Plex server by address, from the optional `get_server_info`.
- **`attrs.now_playing`** lists up to 8 sessions from `get_activity`: `title` (the full title, "Show - Episode"), `kind`, `user` (the friendly name), `state`, `progress` (percent), `decision` (direct play, copy or transcode) and `player`. Player addresses are left out. **`attrs.history`** lists the last 8 plays from the optional `get_history` (newest first): `title`, `kind`, `user`, `at` (Unix seconds), `percent` and `watched`. Both show who watched what, so they're as visible as the tile; a role that may not see the app doesn't see them. The tile lists what's playing under the count and pages to a History view.

**Bazarr.** `missing.episodes` and `missing.movies` are the Demo Home's keys: Bazarr's sidebar badges, the subtitles still wanted, summed over episodes and movies. `wanted` is their sum, the key the *arr tile reads. Health is `attention` with health issues (System → Status) or throttled providers. The reason names the issues as Bazarr lists them ("/tv: Directory does not exist"), or gives their count when `/api/system/health` can't be read. `health.url` is the Bazarr page that shows them, System → Status or System → Providers, and the tile's note links there. Capability `media.library`, like the Demo Home's Bazarr. `attrs.uses` names its Sonarr and Radarr by address, from the optional `/api/system/settings`; only their address fields are extracted, never the API keys beside them.

**Mealie.** Reads the token's household (Mealie 2.0 and later count per household). `recipes` is a series; `recipes`, `categories` and `tags` are also attrs, as in the Demo Home. Polls every 5 minutes. On a 1.x server `/api/households/statistics` is a 404, and the repair turns it into "Mealie v1.12.0 is older than this spec supports".

**Linkding.** Counts the token's user's bookmarks: `bookmarks` is unarchived plus archived (Karakeep's count includes archived ones too), with `archived` and `tags` as attrs. Lists are paginated, so each request asks for one result and reads `count`. The Demo Home has no Linkding series (it's only checked there); `bookmarks` is Karakeep's key. Polls every 5 minutes.

**Karakeep.** `bookmarks` is the key's user's `numBookmarks` (the Demo Home's key and scale). `/api/version` is optional because older releases don't have it; without it the version is unknown and the unsupported-version repair can't fire, so a pre-0.23 server shows `api_changed` instead. Polls every 5 minutes.

**SABnzbd.** The Usenet side of the Download queue tile, beside qBittorrent; capability `downloads.queue`. Polls every 30 s, like qBittorrent. `url` includes SABnzbd's URL base (`/sabnzbd` by default; SABnzbd 3+ also answers at the root). `limit=1` reads the queue's totals without its jobs: job names can be personal, and the tile shows totals.
- `dl.mbps` is `kbpersec` (KiB/s, a string) in Mb/s to 0.1, qBittorrent's key and scale (0–1000, band 0–60).
- `queue` is `noofslots_total`, the jobs in the queue (the *arr tiles' key).
- `left.gib` is `mbleft` (MiB) in GiB to 0.1 (not in the Demo Home).
- **Paused:** the state is `paused` (else `running`) and `attrs.paused` is `true`; health stays `ok`, because a pause is usually the owner's. The Workbench draws that as "off, expected".
- `attrs.speedlimit_pct` is the speed limit as a percentage of the line speed, left out without one; `attrs.disk_free_gib` is the free space on the download folder (`diskspace1`).
- A wrong key is a 403 on recent releases (an auth Repair from the engine) and an error inside a 200 on older ones (the spec's own `auth` repair). Use the API key, not the NZB key: the NZB key can only add jobs.

**Paperless-ngx.** The documents library; capability `documents.library` (new). Polls every 5 minutes. `documents` is `documents_total` and `inbox` is `documents_inbox`, both new keys; the inbox is unknown, not 0, when no tag is marked as an inbox tag. Health is `attention` with "N documents are waiting in the inbox" from `inbox_warn` (default 50) up. The recipe makes a user with view permissions only, so the token can't change anything; Paperless-ngx counts only the documents that user may view, and `/api/status/` (the version) is staff only, so with that user the version is unknown. Spec rather than Go: one header token and two fixed GETs.

**Speedtest Tracker.** The latest result of the v1 API; capability `net.speedtest` (new). Polls every 5 minutes, since tests run hourly or so. `dl.mbps` and `ul.mbps` are `download_bits` and `upload_bits` in Mb/s to 0.1 (`dl.mbps` is qBittorrent's key, on another scale: 0–10000, band 100–1000); `ping.ms`, `jitter.ms` (Ookla's) and `packet_loss.pct` are new keys. Health is `attention` when the last test failed (its numbers are then unknown, not 0) or Speedtest Tracker marked it below the owner's thresholds (`healthy: false`), and `unknown` with "No speed test has finished yet" before the first. `/api/v1/results/latest` answers 404 until then, so it's optional, and the paged list goes first to check the token and count the results. The recipe's token has only the `results:read` ability. Spec rather than Go: one bearer token and two fixed GETs. The list's `page[size]` parameter and the 404 before the first test are from the source, not a live run.

**Beszel.** Host metrics from Beszel's agents; capability `host.metrics` (new). Each system is a resource `beszel:<instance>/system/<record id>`, kind `host`, `part_of` the app: state `online`, `offline`, `paused` or `unknown` (Beszel's `pending`); health `down` when its agent isn't answering, `attention` from `disk_warn` (default 90) percent of disk used up. Metrics are series only on resources without `each`, so a system's CPU, memory, disk and network are attrs with the latest reading (to 0.1; `net_mbps` is Beszel's MB/s in Mb/s), left out while it's down; Beszel keeps their history. The app counts `systems` (all of them, from `totalItems`) and `systems.down`. Polls every 60 s.
- **The token.** Beszel's hub is a PocketBase app, and signing in with a password is a handshake (`auth-with-password`, then the token it answers) that a spec can't express, since a request's templates can't read an earlier answer. So the spec takes a token made ahead of time with PocketBase's Impersonate, for a user with Beszel's `readonly` role, with a long duration; it can't be refreshed, and an expired one is an auth Repair. Go would sign in and refresh it; that's left for when it's asked for.
- **Version:** `/api/beszel/getkey` answers the hub's public key and version (`v`); it's Beszel's, not PocketBase's, and optional, so a hub without it shows no version.

**Gatus.** Gatus's endpoints as checks; capability `checks.uptime`, like the built-in checks, so the Checks widget lists them. No credential: Gatus's API reads without one unless its `security` section is on, and basic auth and OIDC are beyond a spec (basic auth needs Go, as for Nextcloud). Each endpoint is a resource `gatus:<instance>/check/<key>` (Gatus's key, without the leading `_` of an endpoint with no group), kind `check`, named `group / name`, `part_of` the app, from its newest result (`pageSize=1`): `online` and `ok` when it passed, `error` and `down` with Gatus's error or the first failing condition when it didn't, `unknown` before its first check. `response_ms` is the result's duration (nanoseconds in Gatus) in ms, an attr rather than a series, like Beszel's readings. The app is `attention` with "N of M checks are failing". Polls every 60 s.

**Komodo.** The compose stacks Komodo manages, read only; capability `stacks.list` (new). Komodo Core's API is `POST /read` with `{"type", "params"}` in the body and the key and secret in `X-Api-Key` and `X-Api-Secret`; a spec can do that, since a POST with a fixed body counts as a read here (bundled specs aren't gated like installed ones). Each stack is `komodo:<instance>/stack/<id>` (Komodo's ID, stable across renames), kind `stack`, `part_of` the app, with Komodo's `StackState` as its state: `running`, `stopped`, `paused` and `down` (not deployed) are `ok`, `dead` is `down`, `unknown` unknown, and the rest (`unhealthy`, `deploying`, `restarting`, `created`, `removing`) `attention` with Komodo's status line. `server` names its server from the optional `ListServers` (a user without Read on servers still sees stacks). `update_available` is true when any service's image has a newer one; `behind` is true when a git-backed stack's branch has moved past the deployed commit. The app counts `stacks`, `stacks.running` and `updates` (stacks with an update), and is `attention` naming the unhealthy or dead ones. The recipe's service user has Read on stacks and servers only, so the key can't deploy or change anything. Polls every 60 s.

**Arcane.** The compose projects Arcane manages on one environment, read only; capability `stacks.list`, like Komodo. Written from Arcane v2.17.2's source ([getarcaneapp/arcane](https://github.com/getarcaneapp/arcane)): the routes in `backend/internal/project/module.go` and `backend/internal/version/module.go`, the `X-API-Key` header in `backend/api/api.go` and `backend/internal/auth/handler.go`, the list in `backend/internal/project/handler.go` and `children/listing/service.go`, and the types in `types/project/project.go` and `types/base/response.go`. `environment` is Arcane's environment ID: `0` is the host Arcane runs on, a remote one (an agent) has a UUID. The list is paginated: the first 50 projects by name are resources `arcane:<instance>/stack/<id>`, kind `stack`, keyed by Arcane's project ID (a UUID, stable across renames), `part_of` the app; `stacks` is the total from `pagination.totalItems`. Archived projects are left out (Arcane's default). Arcane's statuses are `running`, `partially running` (the state is `partial`), `stopped`, `unknown`, and `deploying`, `stopping` and `restarting` while it acts. A project is `attention` when it's partly running ("1 of 2 services are running") or a service's health check says `unhealthy` ("webserver is unhealthy"), `unknown` when Arcane can't tell, else `ok`. `update_available` is Arcane's `updateInfo.hasUpdate`; `gitops` is true when one of Arcane's GitOps syncs runs it. The recipe's scoped key has only `projects:list`. Polls every 60 s. Not checked against a live Arcane: the `$schema` link Huma adds to each body (unread here) and Arcane's 401 body.

**Dockhand.** The compose stacks on one Dockhand environment, read only; capability `stacks.list`. Written from Dockhand v1.0.56's source ([Finsys/dockhand](https://github.com/Finsys/dockhand), image `fnsys/dockhand`): `GET /api/stacks?env=<id>` in `src/routes/api/stacks/+server.ts`, built by `listComposeStacks` in `src/lib/server/stacks.ts` with the status and health rules of `src/lib/server/stack-status.ts`, and the bearer token in `src/hooks.server.ts` and `src/lib/server/api-tokens.ts`. Each stack is `dockhand:<instance>/stack/<compose project name>` (Dockhand has no other ID for one), kind `stack`, `part_of` the app. Dockhand's statuses are `running`, `partial`, `restarting` (every live container in a restart loop), `stopped` and `created` (defined in Dockhand, never started); containers that exited 0 don't count against a stack. A stack is `attention` when its health is `unhealthy` (naming the containers), `partial` (naming the ones not running) or `restarting`. `stack_health` is Dockhand's own (`healthy`, `unhealthy`, `starting`, or `none` when no container has a health check). `update_available` and `updates` are its digest updates; held and pinned ones aren't counted, as in Dockhand. The token is optional: Dockhand's API answers without a sign-in until its authentication is on, and it reads a bearer token only when it starts `dh_`. In the free edition every user can do everything, so the token isn't read-only; Enterprise roles can limit it to viewing stacks. Dockhand answers `[]` when it can't reach the environment's Docker, so an offline host shows no stacks rather than an error. No version: Dockhand's API doesn't report its own outside `/api/system`, which reads the whole Docker host. Polls every 60 s.

## Limits

- Grants aren't read back for specs (deferred; see `internal/README.md`). Most of these upstreams offer no read-only key, so their credentials can change things even though Cha Dash only reads. The exceptions are Paperless-ngx (a view-only user), Speedtest Tracker (a `results:read` token), Beszel (a `readonly` user's token), Komodo (a service user with Read only), Arcane (a scoped key with `projects:list` only), Cloudflare Tunnel (a Tunnel Read token), borg-ui (a viewer's token) and Gatus (no credential, and its API can't change anything). Dockhand's token can change things in its free edition, which has no roles.
- A fan-out resource (`each`) can't carry series, so Beszel's and Gatus's per-host and per-check readings are attrs, without history in Cha Dash.
- Counts are per user or household where the upstream scopes them so (Mealie, Linkding, Karakeep): an instance shows what its credential's owner sees.
