# 18 · v0.5.1: what 0.5 left open

> **Status: agreed** (2026-11-06). The maintainer settled [P1–P6](#open-questions-p1p6) as recommended ([Decisions](#decisions)). `0.5.0` is tagged and published ([15](15-v0.5.md), [16](16-stacks-parity.md)). This is a patch release: it fixes what 0.5 shipped with known gaps and builds the test harness pieces 0.5's "Done when" still lacks. It adds no new source, no new widget and no new migration unless a fix needs one. Features 15 let slip to "v0.5.x" move to [19 · v0.6](19-v0.6.md) instead, so a patch stays a patch.

**House rule (from [17](17-test-automation.md#the-rule)):** nothing is tested by hand. Every check is an automated test the agent writes and runs, on throwaway data directories, containers and registries. The lab is never a test target: it's only read, by `live:verify`, to check fixtures. Dev servers and builds still need the maintainer's say. **Writing to the lab is an operation, not a test, and needs a go-ahead per run against named targets.**

## Stacks

From [16](16-stacks-parity.md#waves)'s "still open" lists.

- **Remove and `.env`.** Remove deletes the stack's folder, and git doesn't hold `.env`, so restoring from the commit brought back the file but not its environment. Fix ([P1](#open-questions-p1p6)): the node moves the env files at the top of the folder (`.env`, `*.env`) into `<stacks.root>/.chadash/removed/<stack>/<commit>/` before it deletes the folder, and restoring the stack puts the latest back. A removal prunes any older than 30 days. The plan for Remove says so. Tests: `TestRemoveAndRestore` (the same `.env` after a restore) and `TestRemoveKeepsEnvFor30Days` (env files only; gone after 31 days on the node's clock). **Built** (2026-11-06).
- **Pinned after an update rolls back.** A stack update doesn't change the file, but its rollback pinned the file to the old digests, as a deploy's rollback does. Checks then said "pinned by digest" until someone deployed it unpinned. Fix ([P2](#open-questions-p1p6)): an update's rollback leaves the file as it was and pins the old digests in memory, as a deploy's hold does; the containers carry them until the next good update or deploy recreates them. The check no longer treats such a container as held, so it asks about the tag again. Test: `TestUpdateRollsBack` (the file unchanged, no drift, the check moved, the next good push updates) and `TestEngineStackUpdate`. **Built** (2026-11-06). The generated `pins.yaml` P2 named wasn't needed: the running containers already hold the digests.
- **Rejections outside a rollout.** A rollout marks a rolled-back digest so it isn't retried, and so did a single container update. A stack update started on its own didn't. Fix: the Update Center's task hook records it for each of the stack's containers that had an update waiting. Test: `TestStackUpdateRollbackRejectsItsMembers`. **Built** (2026-11-06).
- **Credential helpers** ([P3](#open-questions-p1p6)). A host that keeps its logins in `credsStore` or `credHelpers` couldn't hand them to the node. Fix: the node reads `credHelpers` (per host, first) and `credsStore` and calls `docker-credential-<name> get` when that binary is on its `PATH`, at most every 5 minutes per registry, only for the registries `images.registries` lists. When it isn't on the `PATH`, the login error names the helper and the fix. Test: `TestLoginsFromCredentialHelper`, with a fake helper script on `PATH` (the order, the policy, the cache, an identity token refused, a missing helper's message, nothing secret in the log). Pulls take the helper's login through `Logins.All`, which the same test covers. **Built** (2026-11-06).
- **Two writers, fully.** The warning was on the stack's page and list only, and matched Dockhand, Komodo and Arcane by project name. Fix:
  - by host: the node's `stack.list` and `stack.get` report `up_from`, the compose file the containers were last brought up from when it isn't the stack's own. That's Compose's own `config_files` label, so it catches Dockge, Portainer or a hand-run `docker compose` too, without guessing at each tool's labels; the hub names the tool from the file's folder;
  - in the Inbox: `CheckWriters`, every 5 minutes from the syncer, keeps an attention item per stack with a second manager and resolves it once there's none. A node that doesn't answer keeps its items.

  Tests: `TestListSaysWhoBroughtItUp` (node), `TestTwoWritersAreNamed` and `TestTwoWritersInTheInbox` (hub, with the node away and the item resolving), and the web's `twoWriters` text. **Built** (2026-11-06).
- **Compose's dry run and the host's config.** The dry run builds its own Docker CLI with the default config, so a value it computed and threw away came from the host's `~/.docker`. Fix: `NewSDK` points the Docker CLI's default config directory at an empty one of the node's own. Test: `TestSDKIgnoresTheHostsDockerConfig` sets a `DOCKER_CONFIG` holding a login and finds the default config empty. **Built** (2026-11-06).

## Displays

From [15](15-v0.5.md#wave-34-levels-tv-and-e-ink)'s "still open".

- **Print with absolute times.** Print CSS can't change text, so a printed board says "3 min ago". Fix: a Print item in the board's menu opens `/print/<board>`, which renders it at the ink level, where `ago()` is absolute, and calls the browser's print. It's the signed-in board's route, not a display's. Test: a unit test that the print page renders at ink with absolute times, and a Playwright test that it calls print.
- **TV zoom from the screen.** Every TV gets 1.5×. Fix: the zoom is the viewport's width over 1280 CSS pixels, clamped between 1× and 2.5×, so a 1080p TV whose browser reports 1920 gets 1.5× and a 4K one that reports 3840 gets 2.5×. Test: a unit test over the function, and visual regression at 1920 and 3840.

## Harness

Each of these closes a "Done when" in 15 or 16 that names a person, a device, the lab or time.

### A real node beside the end-to-end hub

Playwright's hub runs the Demo Home with no node, so nothing drives a stack page's buttons against a real Docker Engine. The browser half of 16's layer 4 test, and 17's `bun run e2e:system`, need it.

- `bun run e2e:system` starts the release hub and a release node in throwaway containers on a throwaway network, labelled `chadash.test=<run>`, pairs them through test automation, and runs `web/e2e/system/*.spec.ts`. It removes everything after, and a final step fails on anything left with the label.
- The first specs: deploy a stack, stop, start, take down, remove and restore it, with each tier's confirmation and the virtual passkey for T3; update a stack whose image moved in the test registry; a broken image rolls back; follow its logs.
- It needs images from this commit, which means a build: it runs in CI's End-to-end job, which already builds the release, and never locally without the maintainer's say.

### A week on a display, in test time

15's demo moment is a wall tablet calm for a week. That's time, so it's the test clock:

- A Playwright spec opens a display and runs seven days of hub time (`POST /api/test/clock`) and page time (Playwright's `page.clock`) together, in steps of an hour. It raises and resolves an incident on day 3, drops the hub's socket on day 5, and checks the display at each step: dim or awake, tinted at night, dark in quiet hours, its age shown while the hub is away.
- It also checks what a week would wear out: the page's heap stays under a bound, socket reconnects don't pile up, and the burn-in offset keeps moving.

That replaces "a week on a real board" in 15's Done when. Putting one on the maintainer's wall is still worth doing, as an operation, but it proves nothing a test doesn't.

### Fixtures from real instances

The fixtures of the ten sources 0.5 added were written from documentation, not recorded, so `live:verify` has nothing to compare. Most of those tools run in a container ([P4](#open-questions-p1p6)):

| Source | Throwaway instance | Recorded how |
|---|---|---|
| Technitium, Kopia, Duplicati, Backrest, borg-ui, Zerobyte | Their own images, pinned by digest | `bun run fixtures:record <id>`: start it, seed it through its API, record the integration's requests, sanitize, stop it |
| NUT | `upsd` with the `dummy-ups` driver | The same, over NUT's TCP protocol |
| UniFi | The Network Application's image | The same; slower to start, so it runs nightly, not per push |
| TrueNAS | None runs in a container | Stays documentation-built until a lab instance exists; `live:verify` covers it then |
| Tailscale, Cloudflare Tunnel | SaaS | `live:verify` with read-only tokens from `.env.local`, once the maintainer adds them |

A recording is a layer 3 test: it starts only labelled throwaway containers and never builds. It writes fixtures the contract tests then read. The nightly job re-records and fails on a diff, which is drift caught without the lab.

### Home Assistant loading the integration

ha-chadash's contract test reads `/api/summary` from the newest image, but nothing loads the integration in Home Assistant itself. Its CI starts `homeassistant/home-assistant` pinned by digest, mounts `custom_components/chadash`, creates the config entry through HA's REST API against a demo-mode Cha Dash, and reads the entities back. That replaces "entities on the maintainer's HA" in 15's Done when.

## CI

- **End-to-end without the mirror.** The job installed WebKit's system libraries with `apt` each run. On 2026-11-06 Azure's Ubuntu mirror stalled, and the job ran out its 30 minutes before a test started. Fix: the tests run in Playwright's own image (`mcr.microsoft.com/playwright`), pinned by digest at the version `web/package.json` has, so the browsers and libraries are already there. The build stays on the runner, since the image has no `unzip` for setup-bun, and the runner's `bun` is mounted in. A Renovate regex manager and a Playwright group keep the image and the package in step. The budget and timeout don't change. **Built** (2026-11-06); proven by the job's next run in CI, since it needs the release build.
- **TypeScript 7.1 goes green.** The advisory job failed on TS2367 in `LayoutBoard.vue`, `SectionMenu.vue` and six other components: all comparisons the content mapper narrows wrongly inside a `v-else-if`, [vuejs/language-tools#6306](https://github.com/vuejs/language-tools/issues/6306), still open, none of them ours. Fix: `tools/typecheck/check.ts` skips a TS2367 inside a `.vue` template and fails on anything else. Checked by injecting a type error, which fails it. **Built** (2026-11-06). Part of E10.
- **E3, more fuzz targets:** `nodeproto` frames before pairing, the export importer's sealed bundle, spec templates. Each joins the nightly fuzz job with a seed corpus from its tests.
- **E8, `actions.lock`:** try it beside the SHA pins in one workflow first (Docs), then the rest if it holds.

## Done when

- A removed stack restored from its commit has its `.env` back (engine test), and the kept files go after 30 days on the node's clock.
- An update that rolls back leaves the file as it was and the containers on the old digests, and the next good update clears the pins (`TestEngineStackUpdate`).
- A rolled-back digest isn't retried, whether a rollout or a single action rolled it back.
- A login through a credential helper pulls from the test registry, and a missing helper says which one and what to do.
- Two writers show in the Inbox, matched by labels, by Dockge's folders and by name.
- `bun run e2e:system` drives every stack verb from the browser against a real node, in CI, and leaves nothing labelled behind.
- The week-on-a-display spec passes: dims, wakes for one incident, shows its age while the hub is away, and stays under its heap bound.
- Every self-hostable source added in 0.5 has fixtures recorded from a throwaway instance, and the nightly re-record finds no diff.
- ha-chadash's CI loads the integration in Home Assistant and reads Cha Dash's entities.
- The End-to-end job doesn't call `apt`, and the TypeScript 7.1 job is green.
- The changelog has each user-facing change under `## [Unreleased]`.

## Open questions (P1–P6)

| # | Question | Recommendation |
|---|---|---|
| P1 | Where does a removed stack's `.env` go? | Into `<stacks.root>/.chadash/removed/` on the node, for 30 days. Not to the hub: an `.env` can hold secrets the hub was never given (S4's reasoning) |
| P2 | How does an update's rollback hold the old digests without editing the file? | A generated override, `.chadash/pins.yaml`, cleared by the next good update or deploy. The file stays the person's |
| P3 | Credential helpers: support them, or document `docker --config` only? | Support them when the helper is on the node's `PATH`, and say exactly what to do when it isn't. The node's image ships no helpers |
| P4 | Record fixtures from containers per push or nightly? | Nightly, plus on demand (`fixtures:record <id>`). Some images take minutes to start, and a diff is drift, not a broken commit |
| P5 | HACS default list and brands now, or after 0.6? | Now: both review slowly, and the integration is stable. The agent writes both pull requests; the maintainer says when to open them |
| P6 | Is 0.5.1 a patch only (no features, no migrations)? | Yes. Anything that needs a migration or a new route waits for 0.6. The `.env` fix and `/print/<board>` are the exceptions: no migration, and `/print` is a page, not an API route |

## Decisions

Settled by the maintainer on 2026-11-06: **P1–P6 all as recommended.**

1. **P1:** a removed stack's ignored files, `.env` among them, move to `<stacks.root>/.chadash/removed/` on the node for 30 days; never to the hub.
2. **P2:** an update's rollback holds the old digests in a generated `.chadash/pins.yaml`, cleared by the next good update or deploy.
3. **P3:** credential helpers work when the helper is on the node's `PATH`; otherwise the error names it and the fix.
4. **P4:** fixtures are recorded from containers nightly and on demand.
5. **P5:** the HACS default list and brands pull requests go now, opened on the maintainer's say.
6. **P6:** 0.5.1 is a patch: no migrations or new API routes, except the `.env` fix and the `/print/<board>` page.
