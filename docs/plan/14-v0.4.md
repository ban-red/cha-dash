## The Update Center

v0.3 updates one container or stack through the gate. v0.4 makes it a rollout.

### One list

- **Images** through nodes, as in v0.3.
- **Unraid**: its OS version and its containers. Unraid's answer already wins for its containers (v0.3, U6).
- **PVE apt**: pending packages per host. The integration reads them already, but only with `Sys.Modify` ([V2](#open-questions-v1v14)).
- **Node host packages** (v0.4.x): a new read verb `host.packages` under a new grant, off by default.

Each row says what it is, from and to, and a risk: **patch**, **minor**, **major** or **unknown**. The risk comes from the version numbers, never from a guess.

### Release notes

For an image whose `org.opencontainers.image.source` label points at GitHub, the hub reads the releases between the running and the new tag. That is the hub calling GitHub, so it's a setting, off by default ([V3](#open-questions-v1v14)). Notes are shown as untrusted text: no HTML, links only to the same repository.

### Rollouts

**"Update all", or a selection, becomes a plan**, built by the action engine like any other:
1. **Order.** The graph's `depends_on` decides the order: a database before the app that uses it, Prowlarr before Sonarr. A cycle or an unknown edge falls back to one at a time, in the list's order.
2. **Snapshot first**, per step, where one is possible:
   - a stack in a node's root: a git commit of its files, which owned stacks already have;
   - a container on a PVE guest: a PVE snapshot of the guest, when the Proxmox instance has a control token and the correlator matched the guest (`same_as`);
   - otherwise none, and the plan says so.
3. **Update** through v0.3's gate: pull, recreate, health check, rollback on its own.
4. **Stop on the first failure.** The failed step rolls back; the rest wait, and the Inbox says which ran, which rolled back and which didn't start ([V4](#open-questions-v1v14)).

The rollout is one task with steps, shown on the existing task sheet. Held and snoozed containers are left out and listed. Its tier is the highest of its steps (T2 for containers; T3 if any step is a host's apt upgrade or Unraid's OS).

### Maintenance windows

- A window is a time range, once or weekly, for a set of hosts.
- A rollout can be **scheduled into a window**. It runs as the person who scheduled it, with the step-up taken when it was scheduled, and only if the plan's hash still matches; a changed plan waits for a person ([V5](#open-questions-v1v14)).
- During a window, incidents on its hosts open as **expected**: they show in the timeline but don't notify. One that's still open when the window ends notifies then.

### The node updating itself (v0.4.x)

The node can't recreate itself safely (v0.3, decision 8). The plan: the node starts a short-lived helper container from its own new image, which recreates the node and exits; the hub sees the new version or rolls back through the same helper ([V6](#open-questions-v1v14)).

## Backups

Backups already show up: PVE publishes jobs, `backup.covered` and failures; PBS publishes datastores, verify and prune jobs. v0.4 answers one question: **what in this house isn't backed up, and what's stale?**

### The coverage map

- **Every protectable thing**: guests (PVE), containers with volumes (nodes), Unraid shares and its flash drive.
- **What covers it**: a backup job (PVE, PBS), or a tool that reports its targets (Backrest, Kopia and the others, as specs).
- **How fresh**: the newest good backup's age against an objective. The default objective is 26 hours for anything a daily job covers ([V7](#open-questions-v1v14)).
- **Shown as** a Settings → Backups page and a widget: covered and fresh, covered but stale, not covered, and unknown. The correlator's `same_as` joins a PVE guest to the Docker host on it, so a container inherits its guest's backup unless something backs it up directly ([V8](#open-questions-v1v14)).

Coverage is a graph relation: `backed_up_by`, from the thing to the job, with the newest good run on the edge. The cause engine can then say "stale because PBS's datastore is full".

### Run now, verify now

- **Run now**: PVE's vzdump for one guest, already an action (T2).
- **Verify now**: a PBS verify job for one snapshot or datastore, a new action under PBS's control token (T1: it reads and checks, it changes nothing).

### Sources as specs

Backrest, Kopia, Duplicati, borg-ui and Zerobyte have HTTP APIs that list repositories and their last runs. Each is a spec with a `backups.targets` capability, in the community repo ([V9](#open-questions-v1v14)). Unraid flash backup is read by the Unraid integration.

## Operations

### The incident timeline

Today a resolved incident is kept for 24 hours. v0.4 keeps them:
- **A new table** (migration `00023`), with the incident's lifecycle as rows: opened, changed severity, caused by, acknowledged, resolved. Kept 90 days by default, set under Settings → History ([V10](#open-questions-v1v14)).
- **The timeline** on the resource sheet and as its own page: incidents, the actions that ran (from the audit log), state changes (from history), causes and maintenance windows, on one time axis.
- **Postmortem as text**: copy a time range as Markdown.

### PVE notifications

PVE 8.1 and later send notifications to a webhook target. A new `Signature` route, `POST /api/hooks/pve/{instance}`, takes them, with a shared secret in a header that PVE's webhook target sends ([V11](#open-questions-v1v14)). A backup failure or a fencing event then arrives at once, instead of at the next sync. The body is data: it triggers a sync of that instance and is never shown as is.

### Morning digest

At a time the owner sets, one notification through the existing channels: what happened overnight, what's open, updates waiting, backups stale. It says nothing when nothing happened, unless the owner asks for a daily "all quiet" ([V12](#open-questions-v1v14)).

## Agents: MCP, read and propose

[ADR-0017](../adr/0017-ai-and-mcp.md) already decides the rules: an agent reads and proposes, a person approves with a passkey, nothing is auto-approved. The roadmap review ([D1](09-roadmap-2026.md#7-decisions-this-needs)) moved MCP from after 1.0 to v0.4 as `mcp/v0`. Only the timing changes, so ADR-0017 gets an amendment, not a replacement.

### What exists

- Plans made by an API token wait for a person: `awaiting_approval`, the originator in the audit, approvals bound to the plan hash, an Inbox item for approvers.
- API tokens with scopes and expiry.

### What v0.4 adds

1. **The OpenAPI 3.1 document**, generated from `authz/routes.go` plus a schema per route. A test fails on a route without one, like `TestEveryRouteHasARow`. Served at `GET /api/openapi.json`, public, since it holds no data.
2. **Message IDs.** Every sentence the hub returns gets `{"code", "message", "id", "args"}`, with `message` kept as the English fallback. The web keeps showing `message` for now.
3. **Agent tokens.** A token kind fixed at minting, with ADR-0017's scopes: read scopes narrowable to a lens, tag or host; `logs` separate and off; propose scopes per action. Limits: 3 pending and 20 an hour per token. Minting needs "Agents" turned on in Settings → Security.
4. **Every write from an agent waits**, at every tier, including T1. Plain API tokens keep today's rule.
5. **The MCP endpoint**, `POST /mcp` (streamable HTTP), answering only when Agents is on ([V13](#open-questions-v1v14)):
   - **Resources:** the graph (per viewer, as the token's role sees it), open incidents, a resource's causes.
   - **Tools:** `search`, `get_resource`, `plan` (a dry run with the blast radius) and `propose` (a plan that waits for a person).
   - Generated from the OpenAPI document, so the two can't drift.
6. **Graph text is data.** Names, labels, descriptions and log lines are returned in fields marked untrusted, never in a tool's description or instructions.
7. **The approval sheet** shows the engine's plan, not the agent's words; the rationale is quoted. It counts the agent's proposals today.

**Works with local models**: Cha Dash calls no model. The docs show one setup with a local client and one with Claude Desktop ([V14](#open-questions-v1v14)).

## Reach

What makes Cha Dash findable, checkable and easy to install. It ships with `0.4.0`, not before.

- **Docs site** on VitePress (Vue, like the app), from this repository, published to GitHub Pages:
  - install, upgrade and backups, from `deploy/README.md`;
  - one page per integration, generated from its manifest and recipe, so a new integration has a page without anyone writing one;
  - the API, rendered from the OpenAPI document;
  - the security model and the threat model.
- **Public demo**: the Demo Home on a small host. Visitors are signed in as an Operator; every action runs against the simulator only, and nothing else can be changed (settings, users and tokens are read-only, and the simulator resets every hour). A switch (`CHADASH_DEMO_PUBLIC`) the hub refuses unless demo mode is on.
- **Threat model**, published in the docs: assets, trust boundaries (browser, hub, node, integrations, specs, agents), the attacks each guards against, and what's out of scope. It covers MCP and prompt injection before `0.4.0` ships. The external review stays at 1.0.
- **Distribution**:
  - a one-line installer (`install.sh`) that fetches the compose file, checks the image's signature with cosign when it's installed, and starts it. The script itself is signed and its checksum is in the release;
  - a community-scripts LXC script, submitted once their star threshold is met.
- **Sources**: Beszel (host metrics), Komodo, Arcane and Dockhand (the stacks they manage, read-only) and Gatus (checks), as bundled specs, with Go only where an API needs it. Dozzle as deep links: a container's sheet links to its logs in Dozzle when a Dozzle instance is configured.

## Wave 25 · Contracts

What the parallel waves build on. Each lands with its tests, so waves 26–30 can start from `main` without waiting for each other.

### Messages: `internal/msg`

- **A catalog** of every sentence the hub returns: an ID (`<area>.<what>`, such as `auth.signin_required` or `updates.pinned_by_digest`) and its English text with named parameters (`"{name} isn't running"`). One Go file per area, registered at init, like the integrations.
- **`msg.T(id, args)`** renders the English. A missing parameter or an unknown ID fails the test suite, never a request.
- **The error body gains two fields:** `{"error": {"code", "message", "id", "args"}}`. `code` stays the stable machine code clients switch on; `message` stays the English, so nothing that reads it today changes; `id` and `args` name the sentence for translation. `httpx.Say(w, status, code, msg.M)` writes it; `httpx.Error` stays for the routes not yet migrated.
- **The same pair** on the other surfaces that carry sentences: action refusals and preconditions, plan steps, repairs, incident text and update reasons. Cause hints already have it (`message`, `args`).
- **A test** fails on an `httpx.Error` with a literal sentence once an area is migrated, so the catalog can't fall behind. The migration of the ~256 call sites is mechanical and split by package across the waves.

### The OpenAPI document: `internal/apidoc`

- **A row per route**, keyed by the authz pattern: summary, request type, response type, the error codes it can answer, and whether it streams. Types are the Go types the handlers already encode, read by reflection (struct fields and their `json` tags, slices, maps, pointers, `time.Time`), so the schema can't drift from the code.
- **`TestEveryRouteHasASchema`**, beside `TestEveryRouteHasARow`: a route in `authz.Routes` without a row fails, and so does a row without a route.
- **Security comes from the route table**: `Access` becomes the session requirement, `Token` the token scope (`x-chadash-scope`). `apidoc` imports `authz`, never the reverse.
- **Served** at `GET /api/openapi.json`, `Public`, since it holds no data, and written to `web/public/` at build time for the docs site.

### Migrations

| | Tables |
|---|---|
| `00023_incident_events` | `incident_events` (`id`, `incident_id`, `at`, `kind`: `opened`, `changed`, `caused`, `acknowledged`, `expected`, `resolved`; `data` JSON), indexed by incident and by time. The store keeps them 90 days by default (decision 10) |
| `00024_care` | `rollouts` (`id`, `created_by`, `plan_hash`, `state`, `window_id`, `scheduled_for`, `steps` JSON, timestamps); `maintenance_windows` (`id`, `name`, `hosts` JSON, `starts_at`, `ends_at`, `weekly`, `created_by`, `created_at`); `backup_objectives` (`resource` primary key, `max_age_ms`, `set_by`, `set_at`) |
| `00025_agent_tokens` | `api_tokens.kind`: `api` or `agent` (`CHECK`), `api` for every existing token; `agent_settings` in the settings table (on or off, limits) |

### Actions, topics and tokens

- **Action kinds:** `updates.rollout` (its tier the highest of its steps), `pbs.datastore.verify` (T1), and rollouts reuse `proxmox.guest.snapshot.create` and `docker.container.update`. Each gets its `authz` policy row and its audit kind.
- **Topics:** `backups` (the coverage map, per viewer like `graph`). The timeline is a query (`GET /api/timeline`), not a topic.
- **Agent tokens:** the `agent` kind fixed at minting; read scopes narrowable to a lens, tag or host; `logs` separate and off; propose scopes per action; every write waits for a person at every tier; 3 pending and 20 an hour per token. Minting is refused while Agents is off.
- **Web types** for all of the above in `web/src/model`, so the waves' UIs start from the same shapes.

## Done when

- **"Update all" on the dogfood home survives a deliberately broken image**: the steps before it updated, it rolled back, the rest didn't start, and the Inbox says so.
- A rollout scheduled into a maintenance window runs in it, and its incidents don't notify.
- **Backup coverage is correct for every guest across all 5 PVE endpoints**, and a container on pvedocker shows its guest's backup.
- PBS verify now runs from the hub and its result shows on the datastore.
- A PVE backup failure arrives through the webhook within a minute.
- The timeline on a resource shows last week's incident, the action that fixed it and the state change.
- **An agent proposes a restart through MCP; the owner approves it from the phone with a passkey**; the audit has both sides. An agent token can't approve, can't see a secret, and is refused when Agents is off.
- The OpenAPI document covers every route, and `internal/README.md`, `deploy/README.md` and `CHANGELOG.md` are updated.
- The docs site is published, with a page for every integration and the API from the OpenAPI document; the threat model is on it and covers MCP.
- The public demo runs, and a visitor can run an action against the simulator but change nothing else.
- The one-line installer brings up a hub on a clean Debian host and refuses an image whose signature doesn't verify.
- Beszel, Komodo, Arcane, Dockhand and Gatus each pass `spec test` on a recorded fixture, and a container's sheet links to its Dozzle logs.

## Open questions (V1–V14)

Settled by the maintainer on 2026-11-01: all as recommended, except V1 ([Decisions](#decisions)).

1. **V1 · The 2026 roadmap's leftover v0.3 items.** Recommended: message IDs and OpenAPI in v0.4's contracts, the docs site, demo, threat model and distribution as a "Reach" track in `0.3.x`, and the extra sources as community specs. The alternative is a `0.3.x` release that holds all of them before v0.4 starts, which delays MCP by about the same amount.
2. **V2 · PVE apt without `Sys.Modify`.** Reading pending updates needs `Sys.Modify` on PVE, which also allows changes. Show apt rows only when the owner's token has it, and say so in the recipe (recommended). The alternative, reading `/nodes/{n}/apt/versions`, shows installed versions but not pending ones.
3. **V3 · Release notes from GitHub.** Off by default, one setting, GitHub only, unauthenticated with its rate limit (recommended). A token raises the limit, but it's one more secret for little gain.
4. **V4 · A failed step in a rollout.** Stop and leave the rest (recommended). "Continue past failures" is a later option, and only for steps that don't depend on the failed one.
5. **V5 · Scheduled rollouts and the step-up.** The step-up at scheduling covers the run if the plan hash still matches (recommended). Asking again at run time defeats "while I made coffee"; never asking defeats the step-up.
6. **V6 · The node updating itself.** A helper container from the new image (recommended), or keep it manual and document `docker compose pull`. The helper needs `docker.update` on the node's own container, which today's protection refuses, so it's a narrow, audited exception.
7. **V7 · The default freshness objective.** 26 hours for anything a daily job covers, 8 days for weekly (recommended): a day plus slack. Per-resource objectives override it.
8. **V8 · A container's backup through its guest.** Inherit the guest's backup and say so ("through pvedocker's backup", recommended). It's honest about what a restore would bring back: the whole VM, not the volume.
9. **V9 · Backup tools as specs or Go.** Specs in the community repo (recommended). Only a tool whose API needs Go (signing, streaming) becomes Tier 0.
10. **V10 · Incident retention.** 90 days by default, in Settings → History, beside the metrics' retention (recommended).
11. **V11 · The PVE webhook's secret.** A shared secret in a header, generated per instance and shown once, under a `Signature` route (recommended). PVE's webhook target can't sign a body, so HMAC isn't possible.
12. **V12 · The digest when nothing happened.** Say nothing (recommended), with an opt-in "all quiet" for people who want proof it's alive.
13. **V13 · MCP transport.** Streamable HTTP on the hub only (recommended). A stdio bridge is a small separate binary; leave it to the community or a later release.
14. **V14 · Which clients to document.** One local-model client and Claude Desktop (recommended), tested before `0.4.0`, without endorsing either.

## Decisions

Settled by the maintainer on 2026-11-01 ([V1–V14](#open-questions-v1v14)):

1. **Everything the 2026 roadmap put in v0.3 and v0.3 didn't build is in v0.4**: message IDs and the OpenAPI document in wave 25; the docs site, public demo, threat model, distribution and the extra sources in wave 30. Not as recommended (a 0.3.x "Reach" track and community specs).
2. **PVE apt rows** show only when the owner's token has `Sys.Modify`, and the recipe says so.
3. **Release notes** from GitHub: one setting, off by default, unauthenticated, shown as untrusted text.
4. **A failed rollout step** rolls back, and the steps after it don't start.
5. **A scheduled rollout** runs on the step-up taken when it was scheduled, if the plan's hash still matches; a changed plan waits for a person.
6. **The node updates itself** through a helper container started from its new image, a narrow, audited exception to its own protection (v0.4.x if it slips).
7. **Freshness objectives** default from the schedule: 26 hours for daily, 8 days for weekly; overridable per resource.
8. **A container inherits its guest's backup**, and the map says "through <guest>'s backup".
9. **Backup tools** (Backrest, Kopia, Duplicati, borg-ui, Zerobyte) are community specs; Go only where an API needs it.
10. **Incidents are kept 90 days** by default, set in Settings → History.
11. **The PVE webhook** is trusted by a per-instance secret in a header, on a reviewed `Signature` route; its body only triggers a sync.
12. **The morning digest** says nothing when nothing happened, with an opt-in "all quiet".
13. **MCP** is streamable HTTP on the hub only.
14. **The MCP docs** show and test one local-model client and Claude Desktop, endorsing neither.
