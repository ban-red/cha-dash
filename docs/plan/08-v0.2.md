## What changes in v0.2

v0.1 only reads. Every write path added in v0.2 has to answer four questions before it ships:

1. **Who may do this?** Roles and scopes, checked in one place and tested in CI against every route.
2. **What will it break?** A plan with the blast radius from the Home Graph, shown before it runs.
3. **How do I take it back?** Undo for T1, rollback for deploys, and an honest "this can't be undone" for T3.
4. **What happened?** An audit record for every attempt, including refusals and failures.

The UI for the safety ladder already exists: undo toasts, the hold-to-confirm ring with its blast-radius list, and fix buttons in the Inbox and Needs attention. Today it runs only against the Demo Home (`POST /api/demo/incidents/{id}/fix`), and everywhere else it says "arrives with the action engine" (`web/src/stores/ui.ts`). v0.2 replaces that seam with the real engine.

## Shared contracts (wave 7)

### Code layout
- `internal/action`: `ActionDef`, the registry, the lifecycle (resolve → authorize → plan → approve → execute → verify → audit), per-resource locks, idempotency keys and tasks.
- `internal/authz`: roles, scopes, and `Can(actor, scope, target)`. **The only place** permission decisions are made.
- `internal/audit`: the append-only writer and reader.
- `internal/notify`: channels, routing rules, delivery and retries (wave 10).
- `integrations/<id>/actions.go`: an integration's actions, next to the reads they mirror.
- `cmd/chadash-node`, `internal/node/...`: the node binary and its modules. Shared transport code lives in `internal/nodeproto` so the hub and the node import the same thing.

### Action IDs
`<integration>.<kind>.<verb>`, matching resource kinds: `docker.container.restart`, `proxmox.guest.reboot`, `proxmox.guest.snapshot.create`, `unraid.vm.start`, `qbittorrent.app.pause`, `stack.deploy`. The scope is the action ID, optionally qualified by target: `proxmox.guest.reboot:host=io`.

### The contract
As in [03 · Architecture → Action engine](03-architecture.md#action-engine), with three additions:
- **`Verify`**: a post-condition read through the integration's normal Sync ("the guest reports `running`"), with a timeout. A failed verify is a failed action, even if the upstream call returned 200.
- **`Undo`**: an action ID plus params, computed from the plan (stop → start, snapshot.create → snapshot.delete at T3, never automatic).
- **`Preconditions`**: refuse early with a sentence ("pluto is already stopped") rather than letting the upstream error.

Integrations implement an optional interface, like `Authorizer`:

```go
// Illustrative.
type Actor interface {
    Actions() []action.Def
    Execute(ctx context.Context, req action.Request, t action.Task) error
}
```

The runtime gives `Execute` the same per-instance HTTP client and secrets as `Sync`, but with the **control credential** if the instance has one (see below).

### Control credentials
Read and control credentials stay separate wherever the upstream API allows it (decided in 03). An instance's config gains an optional `control` group with its own secret fields (for example a second PVE token with `VM.PowerMgmt` and `VM.Snapshot`). With no control credential, the instance's actions show as unavailable with a sentence and a link to the recipe that grants them. The existing hint "a read-only token could be upgraded" becomes the way in.

**Unraid is the exception: one key** (decision 6).
- Onboarding asks **"Read-only, or let Cha Dash control Unraid?"** and the consent flow requests the matching scope set.
- The instance records the mode it was set up in. `Test` reads the key's actual grants, so the mode is checked rather than trusted.
- **Read-only** instances show no Unraid actions on tiles or in ⌘K, and run no write probes.
- **Controllable** instances whose key lacks a scope (an older key, or one edited in Unraid) show the affected actions as unavailable. Each says which scope is missing and how to add it: re-run the consent flow with the control scopes, or edit the key under Settings → Management Access → API Keys in Unraid.
- The mode can be switched later in the instance's settings. It re-runs the consent flow and never needs the instance to be deleted.

### Step-up
- A step-up grant lasts 5 minutes on the session and covers T3 actions and revealing secrets. T4 always asks again.
- **Settings → Security → Confirming destructive actions** (`security.step_up`):
  - **Passkey, or password if no passkey** is the default. An owner without a passkey re-enters their password and sees a nudge to add one.
  - **Passkey only** refuses T3+ until a passkey exists.
- Changing the setting is itself a T3 action, so it needs a step-up under the current rule.

### Migrations
- `00006_roles_and_tokens`: role per user (the column exists), `api_tokens` with scopes, expiry and `last_used_at`.
- `00007_actions`: `plans`, `tasks`, `idempotency_keys`.
- `00008_audit`: `audit_events`, append-only and hash-chained: each event stores the SHA-256 of the previous event's canonical JSON. No `UPDATE` or `DELETE` anywhere in the code, enforced by a test that greps the package. `chadash audit verify` walks the chain and reports the first break; Settings → Audit shows the result.
- `00009_nodes`: node identities, pinned keys, status.
- `00011_notify` (planned as `00010`, which went to nodes): channels, rules, push subscriptions, events, deliveries.
- `00014_stack_secret_grants` (v0.2 review): which secret names the hub sent to each stack on each node, so a rollback sends nothing else.

Stacks keep their history in the stacks root's git repository on the node, not in SQLite.

### HTTP
- `POST /api/actions/plan` `{action, target, params}` → a plan with steps, blast radius, tier, undo and whether step-up is needed.
- `POST /api/plans/{id}/approve` executes it. It needs the same session, a fresh step-up where the tier requires one, and the plan's hash, so an approval can only ever run the exact plan that was shown.
- `GET /api/tasks/{id}`. Live progress goes over realtime.
- `GET /api/audit?actor=&action=&target=&since=`, plus an NDJSON export.
- `GET/POST/DELETE /api/tokens`, `GET/PUT /api/users`.
- `POST /api/auth/step-up` (a passkey assertion) → a short-lived step-up grant on the session.
- The demo's `POST /api/demo/incidents/{id}/fix` goes away. The Demo Home registers its actions with the engine like any integration, so the demo exercises the real path.

### Realtime
- A new **`tasks`** topic: running and recent tasks for the viewer, with progress, the current step and the log tail.
- Incidents' `suggested` and `alternatives` actions gain `plan_ready` and an `unavailable` sentence, so the web stops deciding availability itself.

### Roles

| Role | Reads | Actions | Settings |
|---|---|---|---|
| **Owner** | Everything | Every tier; T4 only where enabled | Everything, including users, security and step-up |
| **Admin** | Everything | T0–T3 | Integrations, boards, import/export, stacks, notifications; users other than the owner. Not the security settings |
| **Operator** | Everything | T0–T2 | None |
| **Viewer** | Everything | T0, except actions that read data back (container logs) | None |
| **Household** | Boards only, no Settings, no Inbox detail, the Home Graph without the hub's plumbing | Only actions marked `household: true` (for example pausing Pi-hole), up to T1 | None |

Actions that read data back to whoever runs them (`Def.ReadsData`: a container's logs, which often hold secrets) need Operator or above whatever their tier. Changed in the v0.2 review (below); Viewer and Household could read any container's logs before.

There is exactly one Owner. The Owner can't be demoted, disabled or deleted, except by handing ownership to another user, which is a T3 action. Users are disabled, never deleted, so audit records keep pointing at someone.

### API shapes
Errors use the existing envelope, `{"error": {"code", "message"}}`. The message is a sentence the web can show as-is.

**Plan.** `POST /api/actions/plan` takes `{"action", "target", "params"?}` and answers `200`:

```jsonc
{ "id": "p_01J…", "hash": "sha256:…",           // approve must echo the hash
  "action": "proxmox.guest.reboot", "label": "Reboot win-gaming",
  "target": "proxmox:i_x/qemu/201", "params": {},
  "tier": "T2",
  "confirm": "hold",                               // "none" (T0) | "undo" (T1) | "hold" (T2) | "type" (T3, T4)
  "confirm_text": "win-gaming",                    // only for "type": what must be typed
  "step_up": "none",                               // "none" | "required" (no valid grant on this session) | "fresh" (T4: always)
  "steps": [{ "label": "Ask io to reboot win-gaming" }, { "label": "Wait for it to report running" }],
  "impact": [{ "resource": "app:plex", "via": "runs_on", "depth": 1 }],   // the web's existing Impact shape
  "undo": null,                                    // or { "action", "params", "label" }
  "expires_at": "2026-10-04T14:07:11Z" }           // 2 minutes
```

Refusals: `403 forbidden` (role or scope), `404 not_found` (unknown action or target), `409 precondition` ("win-gaming is already stopped"), `409 unavailable` ("Add a control token to let Cha Dash reboot guests on io", with `"recipe"` naming the instance), `422 invalid` (params).

**Approve.** `POST /api/plans/{id}/approve` takes `{"hash", "typed"?}` and answers `202 {"task": Task}`. It refuses with `403 step_up_required`, `410 plan_expired`, `409 plan_changed` (the hash doesn't match, or the target changed since planning), `422 confirm_mismatch` (typed text), or `409 locked` (another task holds the resource). Only the session that made the plan can approve it. The web runs T0 and T1 by planning and approving straight away, then offers the plan's `undo` as a toast for 10 seconds.

**Task.**

```jsonc
{ "id": "t_01J…", "plan": "p_01J…", "action": "proxmox.guest.reboot", "label": "Reboot win-gaming",
  "target": "proxmox:i_x/qemu/201", "actor": { "kind": "user", "name": "sam" },
  "state": "running",                              // queued | running | verifying | succeeded | failed | cancelled
  "step": "Wait for it to report running", "progress": 0.5,   // both optional
  "log": ["…"],                                    // the last 50 lines, optional
  "started_at": "…", "finished_at": null,
  "error": null,                                   // { "code", "message" } when failed
  "undo": null, "audit": "a_01J…" }
```

`GET /api/tasks/{id}` returns one. The **`tasks`** realtime topic is `{"tasks": {id: Task}}`: running tasks plus the last 24 hours, at most 50. Operators and below see their own; Admin and Owner see all.

**Audit.**

```jsonc
{ "id": "a_01J…", "seq": 4812, "at": "…",
  "actor": { "kind": "user", "id": "u_…", "name": "sam", "via": "web", "session": "s_…", "ip": "10.0.0.12" },
  "action": "proxmox.guest.reboot", "target": "proxmox:i_x/qemu/201",
  "params": {},                                    // secret-typed params are redacted
  "tier": "T2", "result": "ok",                    // ok | failed | refused
  "error": null, "duration_ms": 8123, "task": "t_01J…",
  "prev_hash": "sha256:…", "hash": "sha256:…" }
```

Settings and user changes are audited too, as actions named `settings.<area>.update` and `users.<verb>`. `GET /api/audit?actor=&action=&target=&result=&since=&before=&limit=` returns `{"events": [...], "next": cursor?}`, newest first. `GET /api/audit/export` streams NDJSON. `GET /api/audit/verify` returns `{"ok", "checked", "first_break"?}`. Reading the audit log is Admin and Owner only.

**Step-up.** `POST /api/auth/step-up/begin` returns WebAuthn request options, or `{"method": "password"}` when the fallback applies. `POST /api/auth/step-up` takes the assertion or `{"password"}` and returns `{"until"}`. `GET /api/auth/session` gains `step_up_until` and `step_up_methods`. `GET/PUT /api/settings/security` gains `step_up`: `"passkey_or_password"` (default) or `"passkey_only"`.

**Users.** `GET /api/users` lists `{id, username, role, disabled, has_passkey, last_seen_at}`. `POST /api/users` takes `{username, password, role}`. `PUT /api/users/{id}` takes `{role?, disabled?}`. `POST /api/users/{id}/transfer-ownership` is T3.

**Go seam between the engine and authorization.** `internal/action` defines what it needs, and `internal/authz` implements it, so neither waits on the other:

```go
// Illustrative.
type Actor struct {
    Kind, ID, Name, Role, Via, Session, IP string
    StepUpUntil time.Time
}
type Policy interface {
    // Authorize returns nil, ErrForbidden or ErrStepUpRequired.
    Authorize(ctx context.Context, a Actor, scope, target string, tier Tier) error
}
```

### Authorization test
`internal/authz` holds a table of every route and action with the roles allowed. A test walks the server's router and **fails on any route missing from the table**, then calls each route as each role and checks the result. The node runs the same idea against its RPC verbs. This is the "authorized centrally, tested in CI" line from the roadmap's Done-when.

### Wave 7 status — authz

Built on the authz track (2026-10-04): roles, central authorization, users and step-up. Details in [internal/README.md](../../internal/README.md) ("Roles, authorization and step-up" and the HTTP table).

- **`internal/authz`**: the five roles and their tier caps; `Decide(actor, request, env)` and `Policy` (the engine's seam: `Authorize(ctx, actor, scope, target, tier)`), with T3 needing a step-up grant, T4 needing one from the last minute and a scope listed in the `actions.t4` setting (empty by default), household limited to T0 plus actions marked `household: true` up to T1, and resource-qualified scopes and patterns (`proxmox.guest.reboot:host=pve-a`, `proxmox.guest.*`). Refusals unwrap to `ErrForbidden` or `ErrStepUpRequired` and read as sentences.
- **The route table** (`authz/routes.go`) and **`authz.Guard`** in front of the mux replace `requireOwner`. A route with no row is refused (`500 no_authz_rule`). `TestEveryRouteHasARow` scans the source for every registered pattern and fails on a missing row; `internal/server`'s `TestRouteMatrix` calls every row through the real router anonymously and as each role.
- **Users API** (`authz.Users` over `auth`'s users store), **step-up** (`/api/auth/step-up/begin`, `/api/auth/step-up`, passkey with user verification or the password fallback, its own rate-limit budget), **`security.step_up`** on `GET/PUT /api/settings/security`, and **`authz.ActorFrom(r)`**.
- **Migration `00006_roles_and_tokens`**: `sessions.step_up_until` and the `api_tokens` table. The role constraint already existed in `00001`.

Choices and small departures from the shapes above:
- `step-up/begin` answers `{"method":"passkey","publicKey":…}` (the `method` is added so the web needn't sniff), or `{"method":"password"}`.
- `GET /api/auth/session` carries `step_up_until` (RFC 3339 or `null`) and `step_up_methods` (`["passkey"]`, `["password"]` or `[]`) at the top level, beside `user` and `session`.
- `GET /api/settings/security` also lists `step_up_modes` for the page. `PUT` takes `{posture?, step_up?}`; both are validated before either changes.
- `POST /api/users/{id}/transfer-ownership` takes no body and returns the new owner. `PUT /api/users/{id}` refuses `owner` as a role (`422`); the owner's account is `403` to admins and `409 owner_protected` to the owner.
- Passkey management (`/api/auth/passkeys…`) is open to every signed-in role, for their own account: every role needs a passkey under "passkey only".
- Route roles, where the Roles table left room: integration settings, onboarding, import and export are admin+; correlation reads are viewer+ and decisions admin+; `GET /api/settings/security` is viewer+; `GET /api/demo` is any signed-in role and the demo's fix is operator+.
- The seam's `Authorize` has no room for `household: true`, so the engine passes it with `authz.WithHouseholdAction(ctx)` or calls `Policy.Decide` with `Request.Household`.

**For the merge:**
1. **Seam types.** `internal/authz/authz.go` holds local copies of `Actor`, `Tier`, `ErrForbidden` and `ErrStepUpRequired` with the agreed shapes. Alias them to `internal/action`'s (`type Actor = action.Actor`, …), or make `action` alias these; `authz_test.go` checks `*Policy` satisfies the interface.
2. **Engine wiring.** Build `authz.NewPolicy(store, log)`; read the actor with `authz.ActorFrom(r)`; answer refusals with `authz.WriteRefusal` (`403 forbidden` / `403 step_up_required`); after approving a T4 plan, call `auth.Service.ClearStepUp(ctx, actor.Session)` so T4 always asks again.
3. **Rows.** `POST /api/actions/plan`, `POST /api/plans/{id}/approve`, `GET /api/tasks/{id}` (any signed-in role) and `GET /api/audit`, `/api/audit/export`, `/api/audit/verify` (admin+) are already in the table, marked `Optional`; drop the flag once they're mounted. Any other new route needs a row, or Guard refuses it and the test fails. Register routes on a variable named `mux` with literal patterns (the scan relies on it).
4. **`server.go`.** The route wrapper is now `session` (it only attaches the session; Guard decides the role), not `owner`. Tracks that pass `owner` to their `Register` must switch to `session`.
5. **`store_test.go`** lists `api_tokens` and expects schema version 6; `00007`/`00008` bump both.
6. **Audit hooks.** User and security changes should be audited as `users.create`, `users.update`, `users.transfer-ownership` and `settings.security.update` (the handlers are `authz/users.go` and `security.handlePut`); step-up grants and failures are logged today (`auth/stepup.go`) and could be audited too.
7. **Still to do.** `/ws` admits household, as boards need it; hiding Inbox detail from household is a realtime topic filter that doesn't exist yet. The first-paint snapshot is still owner-only. In the web, `GET /api/onboarding` and the integration settings now answer `403` to roles below admin.

2. The audit cursor goes back as `before=<next>`.

4. Transfer ownership takes `{"typed": "<username>"}` (ignored if unneeded), refuses with `step_up_required` without a grant, and leaves the old owner an admin; the page re-reads `GET /api/auth/session` afterwards either way.

6. `GET /api/users` and `POST /api/users` may answer a bare array/object or one wrapped in `users`/`user`.
7. Admins see Settings → Security for their own passkeys; only the owner sees the security level and step-up.

### Wave 10 status — API tokens (10B)

Built on track 10B (2026-10-06), with tests (`go test -race` clean on the touched packages, Vitest and axe), not merged yet. Details in [internal/README.md → API](../../internal/README.md#api), the HTTP table, and [web/README.md](../../web/README.md) (API tokens, Approvals).

- **Tokens** (`internal/auth/tokens.go`, `internal/authz/tokens.go`): `cdt_<id>_<secret>`, 256 random bits, stored as a SHA-256 and compared in constant time (argon2id buys nothing against a 256-bit random secret and would cost ~19 MiB and tens of ms per request; the reasoning is at the top of `tokens.go`). Every token expires: 90 days by default, 1–365. `last_used_at` and its address are written at most once a minute. Revoked tokens stay listed. `GET/POST /api/tokens`, `DELETE /api/tokens/{id}`, `GET /api/tokens/scopes` (the picker), session only; every role manages its own, admins and the owner see and revoke any. Audited as `tokens.create` and `tokens.revoke`.
- **Authentication**: `Authorization: Bearer cdt_…`, only on `/api/`, never a cookie; the token alone counts (a cookie sent with it is ignored). Other schemes and other bearer tokens aren't read, so a proxy's Basic auth or an identity proxy's token doesn't break sessions. Bad tokens: `401 invalid_token`, or `token_expired` / `token_revoked` once the secret matched; 10 per address, then one per 6 s, then `429`.
- **Scopes**: `graph.read`, `inbox.read`, `audit.read`, `tasks.all`, action IDs and patterns (qualifiable), and `*`. The route table gains a `Token` column (a read scope, `TokenAny` for the engine's routes, or empty for session only); `authz.TokenRoute` decides and Guard answers `403 session_only`. A token acts as its user with the user's **current** role (`authz.WithTokens` over `auth.Service.TokenAccess`, read on every decision), narrowed to its scopes; `audit.read` and `tasks.all` need both the role and the scope.
- **Two new reads** for scripts, since the graph and the Inbox were only on the socket: `GET /api/graph` and `GET /api/inbox` (the role's view).
- **Approvals** (`internal/action/approval.go`, migration `00012`): `action.ApprovalPolicy` (`authz.NeedsApproval`: a token's plans from T2, every agent's plan) turns approving one's own plan into an **Approval** awaiting a person, stored in `approvals`, bound to the plan's hash, with an Inbox item of a new class, **`approval`**, for admins and the owner only (`topics.InboxView.Approvals`). A person approves it in a session (`POST /api/approvals/{id}/approve {hash}`; `approvals.decide` at the plan's tier: admin+, a step-up, made after the request) or denies it (`…/deny`, no step-up). The task runs as the token with `approved_by`. The token polls `GET /api/approvals/{id}` and its task. Approvals expire after an hour (timers, a sweep in `Run`, and on read; restored at start); revoking the token withdraws them; a changed target or a token that can no longer plan it voids them at approval. Audited: `approval.request`, `approval.approve`, `approval.deny` (refusals too), `approval.expire` (actor `system`).
- **T0/T1**: the token approves its own plan; plans bind to `token:<id>` the way a session's bind to the session. **T3+**: refused at planning, as before (`TestPolicyWithTokens`, the HTTP flow test).
- **Audit actors**: `{"kind":"token","id":"tok_…","name":"backup script (sam)","via":"api"}`. `action.Actor` gained `User` and `UserName` (the user a token acts for); `audit.Actor` is unchanged, so the hash chain's canonical form is too.
- **Web**: Settings → API tokens (lazy, axe-tested): the picker, the one-time secret with Copy, the list with last use, revoke. The Inbox's **Waiting for approval** group with `ApprovalItem` (lazy): who asked, the plan's steps and impact, expiry; Approve (hold ring, then a fresh step-up) and Deny. `HoldToConfirm` takes a `hint` id.

Choices and departures:
- **Approvals are a new Inbox class, `approval`**, not `suggestion`: they carry a plan, need a step-up and expire, and must reach approvers only. Viewers and operators see the rest of the Inbox in full but not approvals.

- **Migration `00012`** (pre-assigned); `store_test` expects version 12 and the `approvals` table.

## Wave 10 status — spec actions and carry-overs (10D)
Built on track 10D (2026-10-06). Fakes and fixtures are written from Seerr's API docs; nothing touched a real service. Details in [internal/README.md](../../internal/README.md) ("Tier 1 specs"), [specs/README.md](../../specs/README.md) and [web/README.md](../../web/README.md).

- **Actions in Tier 1 specs.** A spec with an `actions:` section implements `integration.Actor` (`internal/spec/actions.go`). Kept small and safe:
  - **Targets are param-addressed:** `<spec>:<instance>/<target>/<param>`, the param checked against an anchored `pattern` that must refuse `""`, `.`, `..` and `/` (compile fails otherwise) before anything is sent. The runtime routes by the ID's prefix, so it works whether or not the graph has the ID.
  - **A read resolves a target:** a GET whose path may use `{{ target.id }}` only; 404 or 410 is `not_found`, 401 or 403 is `unavailable` naming the instance. Its extracts plus `id` and `name` are what `name`, `state` (the plan's fingerprint), preconditions, labels, bodies and verify read. They ride in `Target.Ref`, which is never persisted or shown, so planning and listing don't read twice.
  - **The write:** POST, PUT or DELETE, one templated path (`{{ target.id }}`, or a required `{{ params.x }}` that is an integer, an enum or has a pattern), every value URL-path-escaped as one segment; an optional JSON body of expressions (not for DELETE). No query, no `%`, no `..`, no secrets or config in paths. Headers are the spec's `source.headers`. Response bodies are never logged or shown; errors are fixed sentences without the URL.
  - **The rest:** tier, title, optional label expression, preconditions (`when` → `message`, the first that holds refuses), verify (`until` over a fresh read, every 2 s, up to a minute, `message` if it never holds), optional undo (another action of the spec on the same target, without params), `household`. Action params are typed fields (string, integer, number, boolean; never secret), validated before planning.
- **Fan-out resources.** A resource template may have `each` (a list expression) and `key` (the element's slug): one resource per element at `…/<id>/<key>`, at most 50, elements without a usable key skipped; `part_of` relates a resource to an earlier one. Metrics can't target them.

## v0.2 review — fixes (node and stacks)

The security review traced seven findings in the node and stacks code. All are fixed, each with a regression test. What changed, and where it differs from what was asked:

1. **Pairing (medium).** The secret is single-use: `Pairing.Redeem` spends it on the enrollment it admits and writes a fresh one, under one lock. The hub also regenerates it on revoke, at start once any node has paired (an upgraded install's secret was already spent), and on `POST /api/nodes/pairing/regenerate` (admin, audited `nodes.pairing.regenerate`, row in `authz/routes.go`). Pairing under a live node's name is refused with `conflict` and leaves the secret unspent; the wave 9 behaviour of revoking the old node on re-pair is gone. Pairing is accepted only from `CHADASH_NODE_PAIRING_FROM` (default: private, loopback, link-local and CGNAT ranges). The node re-reads the pairing file whenever it pairs, so a regenerated secret reaches it without a restart. Tests: `TestPairingSecretIsSingleUse`, `TestRePairAfterLosingTheIdentity` (now: conflict, revoke, then pair), `TestRevokeRegeneratesTheSecret`, `TestFreshInstallPairsByItself`, `TestPairingFrom`, `TestPairingFile`.
2. **`stacks.deploy` is root-equivalent (medium).** The node's guard (`internal/node/stacks/guard.go`) always refuses the socket, `/`, the node's own paths and volumes (read from its container's mounts) and the pairing volume, plus `volumes_from` another container and env/label files outside the stack's directory. It refuses `include` and `extends` from another file outright rather than only outside paths: the node deploys one file, and a nested file could reach out again. The file references are checked in a first loader pass that reads no other file. Policy knobs `stacks.deny` (`privileged`, `host_namespaces`, `devices`, `cap_add`, `host_binds`) and `stacks.bind_roots` are enforced in validate and again in the deploy (on the file with real secret values) and plan; nothing is denied by default. `Plan.RootEquivalent` lists what's allowed but root-equivalent, and the hub puts it at the top of the deploy's steps; the editor shows the same as warnings. Adoption reads only absolute `.yaml`/`.yml` files outside the node's directories. Tests: `TestGuardAlwaysRefuses`, `TestGuardFlagsAndDenies`, `TestGuardSeesSecretValues`, `TestAdoptRefusesPrivateFiles`, `TestStacksDenyPolicy`, `TestRootEquivalentInTheConfirmation`.
3. **`next_key` squatting (low).** `setNext` refuses a key that's any node's key or next key, or a hub key (live or retired); `lookup` tries `public_key` before `next_key` and refuses an ambiguous next key. Test: `TestNextKeySquatting`.
4. **Rollback secrets (low).** Instead of moving stack secrets to `stacks/<stack>/<name>` (which would change the secrets routes, the web and every existing reference), the hub keeps a per-stack grant list, `stack_secret_grants` (`00014`): a deploy records the names its draft references, and a rollback sends only granted names for that node and stack, failing with `secret_not_granted` otherwise. Validation and plans now take names from the hub's own reading of the draft, not the node's reply (the same bug, in the plan path). Tests: `TestRollbackSendsOnlyGrantedSecrets`, `TestPlanSendsSecretsFromTheHubsReading`.
5. **`docker.protect` on stack verbs (low).** The stacks module takes the policy's `Protected` and refuses a plan, deploy or rollback that would recreate or remove a protected container. The node's own project is asked for lazily and again at most once a minute until Docker answers. `docker.writable` also protects the container `SelfInfo` names as the hub. Tests: `TestDeployRespectsDockerProtect`, `TestDeployRespectsDockerProtectOnRemove`, `TestSelfProjectIsAskedAgain`, `TestHubProtectedWhateverItsName`.
6. **Cheap unauthenticated connections (low).** The hub reads the hello under `nodeproto.HandshakeMaxFrame` (64 KiB) and raises the limit for an admitted node (`Channel.SetMaxFrame`); `Recv` grows its buffer with the bytes that arrive; handshakes in progress are capped at 4 per address and 64 overall; unknown and revoked keys and malformed hellos count in the limiter (an admitted node clears its address); refusals of unknown keys log at Info once a minute with a count, else Debug. Tests: `TestRecvGrowsWithTheData`, `TestHandshakeFrameLimit`, `TestSetMaxFrameRaisesTheLimit`, `TestUnknownKeysAreLimited`, `TestHandshakeGate`, `TestRefusalLogSampling`.
7. **Hardening (low).** `nodes.Restrict` became `nodes.Allow(hub, nodes.IntegrationVerbs...)`, an exact list of the Docker verbs integrations use (test `TestAllowedVerbs`). SECURITY.md and deploy/README.md say that env redaction covers `Config.Env` only.

Docs: SECURITY.md, deploy/README.md, internal/README.md (package map, config, HTTP table, Decisions), both stacks READMEs, CHANGELOG.md. No web change: the confirmation's new line is a plan step, and the editor's are validation warnings.

GlyphTip has a 24 px target and a document-level Esc. `scroll-padding` keeps focused elements clear of the floating toolbar and the Save bar. The demo clock's label dropped "UTC".
- **Performance.** The widget picker reads the clock to the minute, so its catalog no longer rebuilds every second.

Not fixed yet:

- ~~**`GET /api/history` over any range (high).**~~ Fixed 2026-10-29, after the history work landed: `Recorder.Query` keeps the newest `points` of the tier it picks when none fits, and the route clamps `to` to now. `from=0` with 20 series had allocated gigabytes, and a far-future `to` panicked in `make`. - **History (medium to low).** A failed write keeps its backlog in memory without a cap; the size-limit trim and Settings → History's stats scan `chunks` each time; recording reads every kind, not just the ones on screen.

- **Accessibility (low).** History's clear confirms don't move focus (the pane was being changed); Discover's and Inbox leads' Dismiss and some working buttons drop focus or use `disabled`; the per-target Test result's live region is created full; the scrollbar thumb is under 3:1; Mosaic's focus order needs checking on a real board. axe doesn't yet cover the picker's target list and error states, the leads item, BannedAddresses, SplitChecks, the drop overlay or the demo banner.

## Decisions
Settled by the maintainer on 2026-10-04:

1. **People scope.** OIDC, forward-auth, the Family board and kiosk tokens move to v0.2.x. v0.2 ships local users and roles. (Later, OIDC and forward-auth were scheduled for v0.3; see [04 · Roadmap](04-roadmap.md#v03-fleet-remote-nodes-everywhere).)
2. **Audit.** Hash-chained from the first migration.
3. **Step-up without a passkey.** Password re-entry as the fallback, with a nudge to add a passkey. **Configurable:** the owner can require passkeys only (see [Step-up](#step-up)).
4. **T4 defaults.** Off by default, including rebooting the hub's own host or the router. The demo enables it for that scope on camera.
5. **Notifications.** Web Push, ntfy and webhook in v0.2. Apprise, email and Home Assistant in v0.2.x.
6. **Unraid control.** One key. Onboarding asks read-only or controllable, and the dashboard handles both. A key missing control scopes gets instructions to add them (see [Control credentials](#control-credentials)).
7. **Breadth integrations.** The roadmap's eight stay in v0.2. They're read-only, so they start alongside wave 7.
