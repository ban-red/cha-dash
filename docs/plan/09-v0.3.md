## Git sync and deploy webhooks

### How a sync runs

1. **Trigger.** The poll timer fires (default every 5 minutes, at least 1, with jitter), or a valid webhook arrives for the sync's remote and branch. One webhook triggers every sync that follows that remote and branch. Triggers coalesce: one sync per stack at a time, and at most one more queued behind it.
2. **Check.** The hub calls `stack.remote.check` on the stack's node. The node lists the remote's refs without fetching. If the tip is the last SHA seen, the sync stops here.
3. **Fetch.** `stack.fetch` does a shallow, single-branch fetch (depth 1) into the node's cache and returns the file at the configured path, the tip SHA, and the commit's subject and author. The cache lives in the node's state directory, not under the stacks root. There is one cache per remote and branch, so when several stacks on a node follow the same remote, only the first fetch after a push goes to the network. Limits: 60 s per fetch, 1 MiB per file.
4. **Gate.** The hub refuses the new tip and says why in the Inbox when:
   - its SHA is the rejected SHA;
   - the sync is held or paused;
   - the stack has drift on disk;
   - its owner can't act any more.
   Otherwise the content becomes the stack's draft, with `source = git:<sha>`.
5. **Plan.** The hub plans `stack.deploy` as the sync's actor. An unchanged plan only records the SHA as seen.
6. **Run or ask.**
   - **Deploy on push:** approve and run.
   - **Draft and ask:** submit to the approvals flow, so the Inbox shows the plan and the commit.
   - A newer tip withdraws an older pending approval.
   - An expired approval leaves the draft in place, deployable by hand.
   - The sync always asks when the content references a stack secret outside its allowlist.
7. **Result.**
   - **Deployed:** records `last_deployed_sha`.
   - **Rolled back:** sets `rejected_sha` to that tip, and the Inbox says "Commit `abc1234` failed its health gate; `def5678` is still running."
   - **Stuck:** the same as today.

### Rules

- **Who it acts as.** A sync belongs to the admin who set it up (`owner_id`), and runs as actor kind `sync` with ID `sync:<id>` and that user's current role.
  - Losing admin, being disabled or deleting the user pauses every sync they own.
  - An admin can take a sync over. Taking it over makes it theirs and needs a step-up.
- **Editing.** A synced stack's editor is read-only and says "Edit `<path>` on `<branch>` in `<remote>`".
- **Rolling back.** A rollback from the web holds the sync at that commit until an admin resumes it.
- **Unfollowing.** Unfollow keeps the files and the history; the stack becomes a normal owned stack again.
- **Protected stacks.** Cha Dash's own stack, and any stack the node protects, can't follow git.
- **Sharing a remote.** One remote URL and branch may feed several stacks, on one node or several, through different paths. They share one webhook. Each sync keeps its own credential, mode and state.
- **Choosing the mode.** Draft and ask is the default. When an admin adds a webhook, the form offers to switch the syncs that follow it to deploy on push, as one step with a step-up, and says what that means: a push deploys without anyone approving it, and a bad commit still rolls back.

### Webhook verification

- **The route.** `POST /api/hooks/{id}`, where `{id}` is `whk_` plus 128 random bits. A hook belongs to a remote URL and branch, not to a stack.
  - An unknown ID and a bad signature both answer the same `401 {"error":"unauthorized"}`.
  - A valid signature answers `202`, even when no active sync follows the hook's remote.
- **The body.** It is read raw through `http.MaxBytesReader`, up to 1 MiB; larger answers `413`, and the next poll catches up. Only the push's `ref` is read from it: a ref that isn't the configured branch answers `202` with `ignored`.
- **Signatures accepted**, each checked with `hmac.Equal` against the hook secret:

| Sender | Header | Signed over | Replay protection |
|---|---|---|---|
| GitHub | `X-Hub-Signature-256: sha256=<hex>` | body | delivery ID (`X-GitHub-Delivery`) seen in the last 24 h |
| Gitea | `X-Gitea-Signature: <hex>` | body | `X-Gitea-Delivery` |
| Forgejo | `X-Forgejo-Signature: <hex>` | body | `X-Forgejo-Delivery` |
| Cha Dash (CI) | `X-Chadash-Signature: sha256=<hex>`, `X-Chadash-Timestamp` | `ts + "." + body`, as in `notify.Sign` | timestamp within 5 minutes |
| GitLab | `X-Gitlab-Token: <secret>` | nothing: compared as a shared secret with `subtle.ConstantTimeCompare` | none; a replay only fetches what is already there |

GitLab's token proves who sent the request but not that the body is intact. That is enough here, because only the `ref` is read and it can only cause a fetch or an `ignored`. The webhook docs warn that a reverse proxy which logs request headers would log this token.

- **Limits.** A token bucket per hook ID and per client IP, keyed like the auth limiter (IPv6 per /64). That limiter is unexported today, so wave 11 moves it to `httpx` for both to share. Failures are counted per hook, and the first in each 10-minute window is audited.
- **The secret.** Shown once, when the hook is made or rotated. Rotating it invalidates the old secret at once.

### Contracts

**Node (`internal/stackproto`, `internal/node`)**

- **Verbs.** Both return `CodeInvalid` for a URL with userinfo and `stackproto.CodeForbidden` (new; the hub answers `403`) for a host outside `stacks.remotes`.
  - `stack.remote.check {url, branch, auth}` returns `{sha, host_key?}`.
  - `stack.fetch {url, branch, path, auth, host_key?}` returns `{sha, content, subject, author}`.
- **Credentials.** `auth` is `{kind: "none"|"https"|"ssh", username?, secret?}`, filled in from the vault per call and never logged. The node scrubs it from errors.
- **Deploy source.** `DeployRequest.Source` (optional, `<url>@<sha>`) becomes a `Chadash-Source` trailer. The commit subject's `by` reads "by git sync for sam".
- **Policy.**
  - New grant: `stacks.sync` (default on).
  - New optional list: `stacks.remotes` (host names or `host:port`; empty means any).
  - Add `PermSync` to `stackproto`.

**Hub (`internal/stacks`, `internal/action`, `internal/authz`)**

- **Actor.** `action.KindSync` (and `authz.KindSync`). `authz.Policy.Decide` resolves its owner the same way it resolves a token's user, and a sync can't step up. `NeedsApproval` returns false for it; instead the syncer sets the new `Plan.RequireApproval` for `mode = ask` and for secrets outside the allowlist, and the engine makes any plan with it wait.
- **The syncer.** `stacks.Syncer` runs one goroutine with a ticker, plus a single-flight per sync. It starts with the hub and stops with its context. A webhook looks up every active sync whose URL and branch match the hook's, and triggers each one.
- **Matching remotes.** URLs are compared after normalizing them: lowercase scheme and host, no default port, no trailing `/` or `.git`.
- **Secrets.**
  - The remote credential is stored at `stacksync/<sync id>/credential`, and the hook secret at `stackhook/<hook id>`.
  - These names are outside `stacks/` so they never show up in the stack secrets list.

## OIDC and forward-auth

### Sign-in flow

1. **Start.** `GET /api/auth/oidc/start?return=/path` makes a row in `oidc_logins` with state, nonce, PKCE verifier and return path, then redirects to the provider. The row expires after 10 minutes, and the return path must be a same-origin path.
2. **Callback.** `GET /api/auth/oidc/callback` checks state, exchanges the code with the verifier, and verifies the ID token: issuer, audience, expiry and nonce.
3. **Look up.** The `(iss, sub)` pair is looked up in `oidc_identities`:
   - **Linked:** apply the group mapping, then `StartSession(…, "oidc")`.
   - **Not linked, provisioning on, and a mapped group present:** create the user with that role, link, start the session.
   - **Otherwise:** "This account isn't linked to a Cha Dash user. Sign in another way and link it from your settings."
4. **Link.** A signed-in user starts the same flow with `?link=1`. The callback links instead of signing in, and needs a step-up first.

### Group mapping

- The settings hold a list of `{group, role}`, with roles from admin down to household; owner isn't offered.
- On each sign-in, a linked user's role becomes the highest role their groups map to. The owner is never changed.
- For a user whose role comes from groups, the role is changed in the provider. The Users page shows "from groups" and doesn't offer the role picker.
- When no group maps, the sign-in is refused, and `auth` emits `user.changed` so open sockets close.

### Step-up

- A user with a passkey steps up with the passkey.
- A user without one is sent to the provider with `prompt=login` and `max_age=0`, and the step-up counts only if `auth_time` is under 60 s old.
- The settings page's "Test" reports whether the provider sends `auth_time`.

### Forward-auth

- **Settings.** On or off; header names (defaults `Remote-User`, `Remote-Groups`, `Remote-Email`); the same group mapping as OIDC.
- **Trust.** Headers count only when the TCP peer is in `CHADASH_TRUSTED_PROXIES`. Otherwise they are stripped before any handler sees them, and the first such request per peer and hour is audited.
- **Sessions.** A request with a valid user header and no session gets a session with method `forward_auth`, for the user linked to that username.
- If the header names a different user than the session's, the session ends.

## Remote nodes

v0.2 pairs a node on the hub's own compose network with the pairing secret in a shared volume ([deploy/README.md → The node](../../deploy/README.md#the-node)). A node on another host pairs today with a copy of that same secret, and is approved the moment it presents it. v0.3 adds **join tokens**: an admin makes one in Settings → Nodes, the node presents it, and the node waits in the Inbox until an admin approves it. The transport, the keys and the registry stay as [ADR-0014](../adr/0014-node-transport.md) built them; this fills in its enrollment paragraph.

### How a node joins

1. **Add node.** An admin opens Settings → Nodes → Add node and gives the host's name (optional) and how long the token lives (15 minutes by default, at most 24 hours). The hub answers once with:
   - the token, `cdj_<secret>.<hub pin>`: 256 random bits, then the pin of the hub key the node should expect;
   - a `.env` block (`CHADASH_HUB`, `CHADASH_NODE_NAME`, `CHADASH_NODE_TOKEN`) and the `compose.node.yaml` command, with copy buttons;
   - the hub address in `CHADASH_HUB`: `wss://<host>/node` from `CHADASH_PUBLIC_URL`, else `ws://<the address the admin is using>:3696/node`. The admin can edit it before copying.
   The hub keeps only the secret's SHA-256.
2. **The node dials.** With `CHADASH_NODE_TOKEN` set and no identity yet, the node generates its key, checks the hub presents the token's pin (as with pairing, the secret never goes to a hub it hasn't authenticated), and sends `Hello.Token`. It prints its key fingerprint in its log.
3. **Enrolled, pending.** In one transaction the hub spends the token (`UPDATE … SET used_at = ?, node_id = ? WHERE id = ? AND used_at = 0 AND expires_at > ?`; no row, no enrollment) and inserts the node as `state = 'pending'`, `enrolled_via = 'token'`. The name rules are today's: the node's `CHADASH_NODE_NAME`, unique among live nodes, and equal to the token's name when the token has one. `hooks` and `secrets` are refused as names (they collide with `/api/stacks/hooks` and `/api/stacks/secrets`).
4. **Waiting.** The hub refuses a pending node's sessions with the new code `pending`. The node logs "waiting for approval in Cha Dash; fingerprint …" once, and retries every 30 s. A pending refusal isn't a failed handshake, so it doesn't count against the address's limit. A node that restarts while pending stays pending.
5. **Approve or reject.** The Inbox shows one item per pending node (class `node`, `node.<id>.pending`, attention). It and Settings → Nodes show the name, the address it dialled from, the fingerprint (with "compare it with the node's log"), its version, the verbs its policy allows, who made the token and when. **Approve** needs a step-up: a node is a new pair of hands on a Docker host, and the hub will send it stack secrets. **Reject** is the existing revoke.
6. **Approved.** The session opens on the node's next retry. When the token asked for it (on by default), approval also adds a Docker integration with the endpoint `node://<name>`, named after the node, so its containers appear without a second form.

### Rules

- **A token is single-use and short-lived.** Spent at enrollment, whatever the approval says. ADR-0014 gives 15 minutes; that stays the default, and up to 24 hours is allowed for a host someone sets up later, since a spent or late token still only makes a pending node. Expired and spent tokens are listed for 7 days, then deleted. An unused token can be revoked.
- **Approval can't be skipped.** No setting approves token enrollments by itself. The pairing secret stays the one way in that approves at once, and only on the hub's own compose network (see Decisions).
- **A pending node expires.** One not approved within 7 days is revoked by the hub (`revoked_by = 'expired'`), and its Inbox item resolves.
- **Approval doesn't widen anything.** The node's policy file still decides what it does; the card shows what that policy allows so the admin knows what they're approving.
- **Rotation and rollover are unchanged.** A token minted before a hub key rollover still works while that key isn't retired; the node learns the new pin on its first session, as paired nodes do.
- **The pairing secret is for the hub's own host.** v0.3's docs stop telling people to copy it to other hosts. `CHADASH_NODE_PAIRING_FROM` keeps working for anyone who relies on it.

### Contracts

**Node (`internal/nodeproto`, `internal/node`)**

- `nodeproto.FormatJoin(secret, pin)` and `ParseJoin(tok)` for `cdj_<secret>.<hub pin>`, beside `FormatPairing`/`ParsePairing`.
- New error code `CodePending = "pending"`. `Hello.Token` carries the secret only (the pin stays on the node), as `Hello.Pairing` does.
- `CHADASH_NODE_TOKEN` (and `CHADASH_NODE_TOKEN_FILE`), read only while the node has no identity. Once it has one, a token in the environment is ignored and the log says it can be removed.
- The client treats `pending` as "wait": log once, retry every 30 s, never give up. `revoked` and `unknown_node` keep today's handling.

**Hub (`internal/nodes`)**

- `nodes.JoinTokens`: `Create(ctx, by, name, ttl, addDocker) (Token, secret, error)`, `List`, `Revoke`, and `redeem(tx, secret, nodeID)` used by the handshake. Secrets compare by hash lookup (`hash` is unique), so there's nothing to compare in constant time.
- `registry.enrollPending` beside `enrollApproved`, and `Approve(ctx, id, by)`, which only moves `pending → approved`.
- The handshake's `!known && hello.Token != ""` case enrolls instead of refusing. `rec.State == StatePending` answers `CodePending`.
- `nodes.Options.OnApproved func(ctx, Record, addDocker bool)`, wired in `cmd/chadash` to create the Docker instance through `runtime.Manager.Create` as the approving user.
- The Inbox source publishes `node.<id>.pending` items from the registry, and resolves them on approve, revoke or expiry.

### Audit and Inbox

- **Audit:** `nodes.token.create`, `nodes.token.revoke`, `nodes.enroll` (actor `anonymous` named `join-token`, with `via: token`, the token's ID and the address; refusals once per address per 10 minutes), `nodes.approve`, `nodes.revoke` and `nodes.expire`, keeping v0.2's `nodes.*` prefix. Approve and revoke already pass through `audited.go`; the token routes get rows.

### Tests

- **Handshake:** a token enrolls pending once; a second node with the same token is refused; expired, revoked and wrong tokens are refused; a token for `alpha` refuses a node named `beta`; a node presents a token to a hub with the wrong pin and sends nothing.
- **Approval:** pending refuses sessions with `pending` and doesn't touch the limiter; approve opens the next session; reject revokes; expiry after 7 days; approve needs a fresh step-up and answers `409` off `pending`.
- **Docker on approve:** the instance is created once, as the approver, and not when `add_docker` was off.
- **Node:** the client's wait loop on `pending`, and that a token is ignored once there's an identity.
- **Routes:** `authz` rows, audit rows, and the literal `tokens` segment.

## Fleet stacks

Owned stacks already work per node: every stacks route and action is `{node}/{stack}`, and the node does the work on its own host. So a node that joins through a token can hold stacks with no change to the pipeline. v0.3 adds what makes a fleet usable: bringing a running stack under a node's root in one step, importers for the tools people leave, and Cha Dash updating itself.

### Bring a stack over (move into the root)

Today a stack another tool deploys can be adopted **in place** (its file stays where it is), or, as [Moving from Dockhand](../../deploy/moving-from-dockhand.md) describes, copied into the root by hand and adopted there. **Move** does the copy for you, keeping the project name so volumes and networks stay.

- **What moves.** The compose file and, when there is one beside it, its `.env`. Nothing else: no data, no build contexts.
- **Where it comes from.** Either the node reads it (a project whose file is on the host, adopted in place or detected), or the hub supplies it (an importer; see below). Supplied content is validated like any draft.
- **Relative paths.** A relative path in the file (a bind source like `./data`, an `env_file`, a `build.context`, a `configs`/`secrets` file) would point somewhere else once the file sits in the root. When the node read the original, it rewrites each to the absolute path it had (`./data` → `/srv/app/data`), so it still names the same data, and the review shows those lines. When the hub supplied the content and the original directory isn't known, a relative path refuses the move and names it.
- **Nothing restarts.** Move writes `<root>/<project>/compose.yaml` (and `.env`), commits it with `Chadash-Kind: adopt` and a `Chadash-Moved-From: <old path>` trailer, and drops the in-place registration if there was one. Like adopting, it runs no compose command.
- **What the first deploy will do** is shown with the move: the plan of the moved file against the running containers. When it would recreate services (the containers came from another compose version, or the content differs from what's running), the review says which, so nobody is surprised later.
- **The old file stays.** The move never edits or deletes it. The stack's page says "A copy stays at `<path>`; the tool that wrote it may still deploy it", until it's gone.
- **Refused:** a protected project, a project already managed, a root directory that already exists, and anything the guard refuses.

`stack.move` is T1, like adopt. Its undo is `stack.unadopt`, which leaves the moved copy and the running containers alone; the original file was never touched.

### Importers

They feed **Move** with supplied content, through Settings → Bring in, in the same review flow as board imports.

- **Dockge** keeps one directory per stack in `/opt/stacks`, the node's default root. Its stacks are already in the root, so `stack.detect` offers them for adoption in place; no importer needed. The docs say so.
- **Portainer**, through its API with an access token (a new read-only Portainer integration, `portainer`, which also shows its stacks as a source): each stack's file and its environment variables, per endpoint. Variables that look like credentials become stack secrets after review, the way imports already move secrets to the vault. A stack is matched to a node by the Docker host its endpoint points at, and the admin confirms the match.
- **Dockhand**, through its API the same way (a new read-only `dockhand` integration), replacing steps 1–3 of the migration guide. Hawser's copies (paths inside its container) are why content is supplied, not read.

### Cha Dash updates itself

Cha Dash's own stack is protected today. v0.3 lets the node on the hub's host deploy it, with one service in scope: the hub.

- **The action.** `chadash.update` (T3, step-up), target `node:<hub host's node>`, params `{image}` (a tag; the node pins its digest). Only the service whose image is `ghcr.io/ban-red/chadash` changes. The node's own service is never touched by it.
- **The node runs it alone.** It pulls, recreates the hub, and gates on the hub container's healthcheck (the image has one) for 120 s. On failure it puts the previous digest back and gates again, as a stack rollback does. It records the result in the stack's history with `Chadash-Kind: self-update`.
- **The task survives the restart.** The hub goes away mid-task. A Def with `Resumes: true` isn't marked `interrupted` at start: the engine calls `Def.Resume`, which asks the node for the last self-update result and finishes the task with it, so the task and the audit record say what happened.
- **Not in v0.3:** updating the node itself (it can't recreate its own container safely), and updates of other stacks, which is the Update Center's job.

### Contracts

**Node (`internal/stackproto`, `internal/node/stacks`)**

- `stack.move {stack, from_path?, content?, env?}` → `{commit, rewrites: [{line, from, to}], plan}`. Exactly one of `from_path` and `content`. Perm `stacks.adopt`.
- `stack.selfupdate {image}` → a task stream like `stack.deploy`, then `{outcome, previous, current}`; `stack.selfupdate.result` → the last one. New perm `stacks.selfupdate`, **off by default**; `compose.yaml` turns it on for the hub's host only.
- `stack.detect` gains `moveable` and `move_refusal` beside `adoptable`.

**Hub (`internal/stacks`, `internal/action`)**

- Actions `stack.move` (T1) and `chadash.update` (T3), and `action.Def.Resumes` with `Def.Resume(ctx, task)`.
- The importers live in `internal/importer/portainer` and `internal/importer/dockhand` and return stacks as a new plan kind (`Plan.Stacks`), applied as `stack.move` calls after review.
- Settings → Stacks gains the buttons it lacks: Move, and Unadopt (today only the API has it).

No migration: moves live in the node's git history, and imports are recorded in `imports` (`00016`) as board imports are.

### HTTP

| Route | Access | What |
|---|---|---|
| `POST /api/stacks/{node}/{stack}/move/preview` | Admin | `{from_path?, content?}` → the rewrites, the plan and any refusal; saves nothing |
| `POST /api/actions/plan` with `stack.move` / `chadash.update` | Admin | Through the engine, as other stack actions |
| `GET /api/nodes/{id}/self-update` | Admin | The last self-update result and whether this node may run one. Under `/api/nodes`, not `/api/stacks/{node}/…`, where it would shadow a stack named `self-update` |

### Tests

- **Move:** from an in-place stack and from supplied content; relative paths rewritten when the original is known and refused when it isn't; an existing root directory, a protected and a managed project refused; nothing runs on the stub Docker; the trailer; unadopt afterwards keeps both copies.
- **Importers:** recorded fixtures for Portainer's and Dockhand's APIs (sanitized as `testdata/` requires), secret-looking variables moved to the review, and endpoint-to-node matching.
- **Self-update:** a good image updates; a bad one (failing healthcheck) rolls back; the node's own service is refused; the perm off refuses; a hub restart mid-task finishes the task from `stack.selfupdate.result`.

|---|---|---|
| Correlation across Unraid, Docker, Traefik and apps | Built in v0.1 and v0.2 ([`internal/correlate`](../../internal/correlate/README.md)): `same_as` to a primary, `runs_on`, `routes_to`, `monitors`, Compose `depends_on`, suggestions and decisions | Nothing new |

### Apps say what they use

An integration publishes the services its app is set up to use, as it knows them: an address. It doesn't guess which resource that is. The correlator joins the address to an app, a route or a container, as it already does for an app's own URL, and publishes `depends_on`.

- **The attr.** `uses`: a list of `{"role", "url", "name"}` on the app resource. `role` is a word the copy can use (`download client`, `indexer`, `media server`, `MQTT broker`). `name` is what the app calls it ("qBittorrent"), for the copy when nothing joins.
- **The rule.** For each entry, the correlator looks for the app whose URL it is, then a route whose open URL covers it, then a container that publishes its `host:port`, with the slots and confidences it uses today. A join publishes `app depends_on <resource>` with `rule: uses`. Strong when the address matches, weak (a suggestion) when only the name does.
- **No credentials.** An entry carries no username, password or API key, even where the app's API returns them (Sonarr's download client settings can). The integration drops every field but host, port, path and TLS.
- **First apps** ([G4](#open-questions-g1g10)):
  - Sonarr, Radarr and Lidarr: their download clients and indexers (`/api/v3/downloadclient`, `/api/v3/indexer`).
  - Prowlarr: the apps it syncs to.
  - Bazarr: Sonarr and Radarr.
  - Seerr: Sonarr, Radarr and its media server.
  - Tautulli: Plex.
  - Frigate: its MQTT broker.

### Caddy and NPM

Both publish `route` resources shaped like Traefik's (`rule`, `url`, `upstream_addr`, `entrypoint`), so the correlator's `routes_to` and `monitors` work unchanged.

- **Caddy** reads the admin API (`GET /config/apps/http/servers`): each route's hosts and paths, and its `reverse_proxy` upstreams. The admin API has no authentication and can change everything, and by default it answers only on localhost. The recipe says to expose it on a private address only, and the integration raises a security finding when it answers with no auth from Cha Dash's network, as Traefik's open API does today ([G5](#open-questions-g1g10)).
- **Nginx Proxy Manager** reads `GET /api/nginx/proxy-hosts` with a token from `POST /api/tokens`. The recipe asks for a user that can only view proxy hosts. The token lasts a day, so the integration renews it before each sync that needs it.
- Probably a spec each (Tier 1). If NPM's token renewal doesn't fit the spec format, it's Go.

### Cause hints

**Where they run.** In the hub, over the live Home Graph and the health history, for every primary resource that isn't `ok` and every open problem. They are hints: a sentence and the resource it points at, never a verdict that changes health or opens an incident.

**The walk.** From the symptom, follow what it needs, up to three steps:

| The symptom… | needs |
|---|---|
| `runs_on`, `part_of`, `depends_on` or `stores_on` X | X |
| is a route that `routes_to` X | X |
| is a check that `monitors` X | X |
| has X that `provides_network_for` it | X |

Each step goes through `same_as`, so Unraid's view of a container leads to Docker's.

**A candidate cause** is a resource on the walk that:
- isn't `ok` now; or
- changed state in a window around when the symptom began: from 30 minutes before to 2 minutes after, since polls lag ([G3](#open-questions-g1g10)). "When it began" and "changed state" come from `history.states`. A state change is a health change, `stopped`, `gone`, or one of the events below.

**Events** read from what the sources already publish:
- a container's `oom_killed`, `exit_code`, `finished_at`, a `restart_count` that went up, or a recent `started_at`;
- a guest or host that started recently (uptime);
- an incident open on the resource (its title).

**Ranking.** Up to three causes, the root first. The root is the candidate furthest up the walk that has no cause of its own. Then nearer candidates, then by how close in time. A cause on the root's path that only says the same thing again ("the qBittorrent app is down" when its container was OOM-killed) is left out.

**The sentence** names the cause, then why it matters to the symptom, from the relation:
- "qBittorrent's container was OOM-killed at 14:03. Sonarr uses qBittorrent as its download client."
- "stork has been at 95% memory since 14:00. files runs on it."
- Each sentence also gets a message ID with its arguments, for the translation work planned for 1.0.

**Where they go** ([G1](#open-questions-g1g10)):
- A new `causes` topic: `{"<resource>": [cause]}`, each cause `{text, resource, at, rule}`, for the symptoms that have any. Tiles and sheets show the first cause under the health ("because …"). The resource sheet lists them all.
- Open problem incidents gain them in `causes`, after the integration's own and the correlator's PBS causes. This uses the same "remember what I added" pass the correlator runs today.
- Repairs, hints and security findings get none.

**Demo mode** ([G2](#open-questions-g1g10)): the engine runs over the Demo Home as over a real home. The simulator stops writing causes for its own stories, and keeps them as the expected answers in a test.

### The Atlas

A map of the home: what runs on what, what depends on what, and how traffic gets in. The same component serves a full-screen lens (from ⌘K, and from a resource's sheet, centred on it) and a Hero widget (8×4) on a board.

- **Layers** the person toggles:
  - compute: hosts, guests, engines and containers, by `runs_on` and `part_of`;
  - network: the router, `provides_network_for`, routes and `routes_to`;
  - storage: arrays, pools, datastores, `stores_on`;
  - backups: `backed_up_by`, with each job's last result;
  - dependencies: `depends_on`.
- **Only primaries.** A node is a resource without an outgoing `same_as`. Its health is the worst of its members', as tiles already merge it.
- **Layout.** Our own layered layout, no graph library ([G7](#open-questions-g1g10)): the router and network at the top, then hosts, guests and engines, containers, apps, and routes at the edge. It's computed in the browser and the same every time for the same graph. Containers on one engine fold into a group above a size, with a count; selecting the group opens it.
- **Health and causes.** Nodes carry health colour, shape and a glyph, never colour alone. Selecting a node that isn't `ok` lights the path to its first cause and dims the rest. That's the demo moment.
- **Interaction.** Select to see the resource's sheet, pan and zoom, and arrow keys move between neighbours along edges. The Hero widget keeps the layers and the zoom it was saved with.
- **Accessibility** ([G8](#open-questions-g1g10)): the canvas has a list view beside it with the same nodes, grouped by layer and nested by `runs_on`, with health and cause in words. Keyboard and screen reader users use the list; the canvas follows the selection. Axe runs on both.
- **Budget.** A lazy chunk, outside the 150 kB initial JS. It reads the `graph` and `causes` topics the page already has, and adds no request.

### Contracts

- **Graph:** the `uses` attr on apps, and the correlator rule `uses` with its confidences. No new relation type.
- **Topics:** `causes`, readable with a session or a token with `graph.read`, like `graph`.

### Wave 16 as built

- **`uses`.** `integration.AttrUses` and `integration.Use` (`{role, url, name}`). `integration.UseURL` builds the URL from scheme, host, port and path and drops any user, query or fragment, so wave 18's integrations can't pass a credential through it.
- **The rule** (`internal/correlate/uses.go`) runs after Compose's dependencies. Per entry, the first of these that matches: the app at that URL; the most specific route covering it, or the app behind it when the correlator joined one; the container publishing its `host:port` or bridge address, or the one app in it. A URL that isn't http(s) joins by host and port. The slot is per entry (`uses:<app>:<url or name>`), so two matches for one entry become suggestions. A name alone suggests when exactly one other app has that name or type. Confirmations land through `confirmedRest`, as for other rules.
- **Causes.** `topics.Cause` and `topics.Step`, and `topics.CauseSet`: `Replace` takes the whole set, keyed by symptom, and keeps the paths out of the topic; `Of` returns one resource's causes with paths. Household sees the causes of resources its graph shows (`CausesSource`, `HouseholdSees`), on the topic and on `GET /api/causes`. A cause's own resource isn't filtered: the sentence names it as a tile would. Nothing writes causes yet.
- **Web:** `Use`, `CauseHint`, `CauseStep`, `CausesDoc`, `CausesResponse` in `model/types.ts`, and `causes` on `LiveDoc`. The live store doesn't subscribe to `causes` yet; wave 17 does, with the first reader.

### Wave 17 as built

- **A package of its own**, `internal/causes`, rather than `internal/correlate`. In demo mode the correlator runs over the instances' private graph, while the cause engine has to run over the Demo Home the page reads. Its rules are in its [README](../../internal/causes/README.md).
- **Remembered events.** A container that was OOM-killed and restarted no longer says so. The service remembers OOM kills, exits and restart-count increases for an hour, so Sonarr's hint still names the OOM kill after Docker restarts qBittorrent.
- **One root, then the nearest.** The root is the candidate no other candidate's walk passes through, the furthest away. The rest follow nearest first, then closest in time.
- **Nothing that began after the symptom.** A problem or an unhealthy state that began after the window's end is left out. Without that rule, the Demo Home's sandbox, broken since 11:20, was blamed on stork's memory pressure from 13:30.
- **Integrations aren't symptoms.** Their trouble is a repair.
- **The simulator keeps its incidents' causes.** They stand in for what each integration says itself, and the engine skips a hint whose resource an incident already names. So in the Demo Home the engine adds to the causes topic, not to incidents. The suite (`internal/demo/causes_test.go`) drives the day from 13:30 to 14:05 and checks every resource's first cause:
  - Sonarr, Radarr and qBittorrent: the OOM kill;
  - Nextcloud: its container's restart at 07:10;
  - files: stork's memory problem.
- **Web.** The live store subscribes to `causes`. A tile's state line says "because …" with the hint's `args.what` in place of its own "likely: …" guess. The sheet lists the hints under **Because**. The first paint doesn't carry causes yet, so a tile shows its guess until the socket's snapshot arrives.
- **Times** in the sentences are the hub's local time, 24-hour; the page's 12/24-hour setting doesn't reach them.

### Wave 18 as built

- **`uses` is cleaned centrally.** The emitter rebuilds every `uses` attr with `integration.CleanUses`, for Go integrations and specs alike:
  - only `role`, `url` and `name` stay;
  - URLs are rebuilt without user, query or fragment;
  - at most 32 entries are kept.

  So a spec expression can't leak a key, and each integration's test checks its exact entries.
- **The *arr apps** read `/downloadclient` and `/indexer` (Prowlarr: `/applications`) on their 10-minute slow cadence. A download client's address comes from its `host`, `port`, `useSsl` and `urlBase` fields; an indexer's or an application's from `baseUrl`. Disabled entries and blackhole clients are left out. The roles are `download client`, `indexer` and `sync target`.
- **Specs.** Bazarr reads `/api/system/settings`, Seerr `/api/v1/settings/{sonarr,radarr,plex,jellyfin}`, and Tautulli `get_server_info`. All are optional requests, and only the address fields are extracted. The roles are `series manager`, `movie manager` and `media server`.

- **The fixtures are synthetic.** No real Caddy or NPM was read, so "Done when" still needs one of them on a real or recorded setup. Neither has a bundled logo yet, so both show a badge.

## The Update Center and the spec format

> **Status: agreed, fourth pass** (2026-10-31; U1–U6 and P1–P5 settled as recommended, [Decisions](#decisions) 21–31). Waves 21–23 are built; see [Wave 22 as built](#wave-22-as-built) and [Wave 23 as built](#wave-23-as-built). The roadmap's "Update Center, minimal" and "spec format `v1alpha1`" ([09 · 2026](09-roadmap-2026.md)) are both small given what v0.2 and v0.3 already built. They share nothing but the release.

### The Update Center, minimal

What's built already:
- The node's `docker.update` grant: pull an image, and recreate a container from it.
- A stack deploy with a health gate and a rollback.
- Self-update's gate and rollback for one container, now fixed and run live (`08795f4`).
- Unraid's `unraid.container.update`.

Missing are knowing that an update exists, a place that lists them, and a gate and rollback for a container that isn't in a stack.

**Detection.**
- The node checks each running container's image tag against its registry: a `HEAD` on the tag's manifest, compared with the local image's registry digest. Docker Hub doesn't count `HEAD` requests against its pull limit.
- It checks at most every 6 hours, and on demand from the page. The hub only asks; the registry traffic comes from the node's host, which already pulls the images.
- New verb `image.check`, read-only, under a new grant `images.check` ([U1](#open-questions-u1u6-p1p5)).
- An image built locally, pinned by digest, or from a registry that needs a login is "can't check", with the reason ([U2](#open-questions-u1u6-p1p5)).
- Unraid containers use Unraid's own update status where its API reports one. Nothing is checked twice: an Unraid container also seen through a node goes by Unraid's answer, since Unraid will do the update.

**What's published.**
- A container gains `attrs.update`: `{state, current, latest, checked_at, reason}`. `state` is `current`, `available`, `cant_check` or `held`.
- An app whose own API reports `update_available` (Pi-hole, Seerr) keeps it as it is. That's the app updating itself, which the Update Center only links to.

**The page.**
- Settings → Updates, and an Inbox count of updates available, as quiet `info` items, never in Needs attention ([U3](#open-questions-u1u6-p1p5)).
- One row per container with an update: its host or node, its stack if any, the tag, how old the new digest is, and when it was checked.
- Rows are grouped by host.

**Updating one** (T2, with a hold-to-confirm listing the blast radius). The update follows how the container is run:
- **In an owned stack:** the stack's deploy with `pull`, through its usual gate and rollback. Nothing new.
- **A plain container on a node:** pull, recreate, the health gate, and a rollback to the previous digest. This is self-update's sequence, moved out of `selfupdate.go` into a shared `updateContainer` for any container but the hub's and the node's own.
- **Unraid-managed:** `unraid.container.update`.
- **Anything else** (a compose project the node doesn't own, a container on an engine read without a node) gets no Update button. The page says what would make it updatable: adopt the stack, or add a node.

**Hold and snooze.** Hold a container at its current image until you release it, or snooze an update for 7 days or until a newer digest appears. Holds are hub-side rows and audited, `update.hold` and `update.release`.

**Not in v0.3** (the full Update Center, v0.4): staged and dependency-ordered rollouts, updating several at once, release notes, scheduled maintenance windows, and the node updating itself.

### The spec format `v1alpha1`

What's built already: 9 bundled specs in `chadash/v1alpha1`, the engine, fixture tests, and actions on param-addressed targets. The format is documented in `internal/README.md`, but only as a comment-annotated sample.

**Publish the format.**
- A JSON Schema for `chadash/v1alpha1`, generated from the engine's Go types so the two can't drift. It's served at `/api/specs/schema/v1alpha1.json` and published on the docs site.
- `internal/README.md`'s sample becomes a reference page.
- ADR-0025 is written and accepted ([P1](#open-questions-u1u6-p1p5)). "Alpha" means the format can change; a change ships a new `apiVersion` and a migration, and the engine loads both for one minor release.

**A test command for authors.** `chadash spec test <spec.yaml> <fixtures/>` runs a spec against its recorded responses and prints the resources, metrics and repairs it publishes, with the same checks as the bundled specs' tests. `chadash spec lint` checks the schema and the load-time rules: patterns, templates, no secrets in paths. Both run with no hub.

**Install from Settings** ([P2](#open-questions-u1u6-p1p5)).
- Settings → Integrations → Add → **From a spec file**: the owner pastes or uploads a YAML. The hub validates it like a bundled spec and shows what it reads and which actions it adds. It's installed with a step-up.
- Installed specs live in a new table (`installed_specs`, migration `00022`): the YAML, its SHA-256, who installed it and when, and its source. They're marked "installed" on the Add list.
- An ID a bundled spec uses is refused.
- Removing a spec with instances is refused until the instances go.
- Replacing a spec with a new version shows a diff of what changes.

**What an installed spec can do.**
- The same as a bundled one, which is already narrow. Requests go only under the instance's URL, secrets only into headers and queries the spec names, expressions are sandboxed, and there are at most 16 actions, each with its declared tier.
- The risk is an action that lies about itself: an "Approve" that deletes. So an installed spec's actions stay off until the owner turns them on for that spec, after a page listing each action's method, path and tier ([P3](#open-questions-u1u6-p1p5)).

**The community repo** ([P4](#open-questions-u1u6-p1p5)).
- `ban-red/cha-dash-specs`: one folder per spec with its YAML, recorded fixtures (required), a README and a recipe.
- CI runs `chadash spec lint` and `chadash spec test`, and a maintainer reviews every pull request.
- The hub doesn't fetch the repo in v0.3: you copy a spec from it into Settings. Browsing it from the hub, with an index and pinned versions, comes later ([P5](#open-questions-u1u6-p1p5)).

### Contracts

- **Migration `00022`:** `installed_specs` and `update_holds`, both `STRICT`, with times in Unix milliseconds and prefixed IDs.
- **Node:**
  - the `image.check` verb and the `images.check` grant;
  - `updateContainer` shared by self-update and plain containers;
  - a `container.update` verb under `docker.update`.
- **Hub:**
  - the update checker in `internal/stacks`, or a new `internal/updates` that imports only `nodes` and `graph`;
  - the `update.*` actions;
  - spec install and removal in `internal/spec` and the `specs` registry, with installed specs registered next to the bundled ones at start.
- **HTTP:** each new route gets its row in `internal/authz/routes.go`.
  - `GET /api/updates` and `POST /api/updates/check`;
  - `POST /api/updates/{resource}/hold` and `DELETE /api/updates/{resource}/hold`;
  - `GET /api/specs/schema/v1alpha1.json`, which is public;
  - `GET`, `POST` and `DELETE /api/specs/installed`, owner only, with a step-up to install.
- **CLI:** `chadash spec test` and `chadash spec lint`.

### Tests

- **`image.check`** against a fake registry:
  - a new digest is `available`;
  - a local build and a digest pin are `cant_check`, each with its reason;
  - a 401 from the registry is `cant_check` "needs a login";
  - the 6-hour limit holds.
- **`updateContainer`:** the self-update tests run on it unchanged, plus a plain container's rollback, and a refusal for the hub's and the node's own containers.
- **Unraid:** a container Unraid manages goes by Unraid's status, once.
- **Holds:** a held container's newer digest stays `held`; a snooze ends at 7 days or at a newer digest.
- **Specs:**
  - the schema validates every bundled spec, and rejects each load-time rule's counterexample;
  - `spec test` on a bundled spec prints what its Go test expects;
  - an installed spec registers after a restart;
  - a clash with a bundled ID and a removal with instances are refused;
  - its actions stay off until they're turned on, and a plan for one refuses with a sentence that says so.

### Wave 22 as built

- **Node.** `image.check` sends the registry a `HEAD` for the tag's manifest itself (`registry.go`), with Docker Hub's anonymous token and no credentials. Docker's `/distribution/{ref}/json` also GETs the manifest, which Docker Hub counts as a pull, so it's only the fallback for a registry the node can't reach directly. Answers are kept 6 hours, failures 15 minutes, and a check cut short keeps nothing. `{"fresh": true}` asks again for answers older than a minute, and only the Update Center's Check now sends it: an instance's own refresh reads the node's cache. `container.update` is self-update's sequence for any writable, running container. - **Nodes and self-update:**
  - **Approval.** It happens in Settings → Nodes. `nodes.Options.OnApproved` also takes the approver, so the Docker instance is audited as theirs.
  - **Self-update.**
    - It recreates the hub's container from its own settings. It never edits the compose file, so `docker compose up -d` goes back to the file's tag; `deploy/README.md` says to pin the tag.
    - It turns on with `CHADASH_NODE_SELFUPDATE` beside the hub.
    - It refuses a hub with no registry digest to roll back to.
  - **The `stack.move` action takes only `from_path`.** A compose file would put credentials in plans and audit records. The importers need a path of their own on the hub.
  - **Resume across a shutdown.** A resuming task whose `Execute` is cut off by the hub stopping stays `running`, to be resumed.

### Wave 15 review

Four reviewers read waves 11–14: git sync, OIDC and forward-auth, nodes with move and self-update, and authorization and audit across all of them. Every finding was checked against the code. All are fixed, each with a test.

- **High:**
  - "Test remote" sent a sync's saved token to any URL, with no step-up. It now goes only to the remote it was saved for, and a token never goes over `http://`.
  - Step-up through the provider ignored "passkey only" and passkey users. It now follows the step-up rule.
- **Medium:**
  - **Retargeting a deploy-on-push sync.** Changing its branch, path, credential or allowlist needed no step-up; now it does, and rejected commits stay rejected across the change.
  - **Root-equivalent changes.** Deploy on push now asks before them, and asks when it can't read the plan.
  - **The `/node` limiter.** It ran before the key was known, so one address could lock out every remote node. Known keys now always get through, and failures count per /64.
  - **Group roles.** Role changes from groups, and provisioned accounts, are audited. Admins can lower a role from groups. Forward-auth applies groups to every session of a linked user.
  - **Audit flooding.** It was possible through the OIDC callback and through join-token refusals; both are throttled.
  - **Git fetches.** They are capped at 64 MiB, and idle caches are pruned after 14 days.
- **Low (21):**
  - **Git sync:**
    - The last 20 rejected commits are kept, checked against the commit fetched.
    - Redirects obey `stacks.remotes`.
    - Refusals while busy are retried.
    - A new hook switches only its maker's syncs.
    - The per-hook limit applies after the hook is found.
  - **Anonymous actors.** Webhook and join-token refusals are audited as `anonymous`.
  - **Compression.** Hook secrets are never compressed.
  - **Forward-auth:**
    - It makes sessions only on page loads.
    - Bans apply to it and to the OIDC callback.
    - Repeated headers are ignored.
    - Settings → Sign-in shows the groups header the proxy sends.
  - **Linking and step-up through the provider.** They start same-origin only, and the link re-checks the step-up.
  - **Move:**
    - It reads only regular files, never through a symlink.
    - It stages under `.chadash/`.
    - A join token can't name a node `local`.
  - **Self-update.** It gates on the container it recreated.
  - **Tests.** Every step-up route and the webhook's signature row now have tests.

Still open: the overall handshake gate on `/node` can be filled by strangers, as before.

## Decisions

Settled by the maintainer on 2026-10-22:

1. **GitLab's token is accepted in v0.3.** It is compared in constant time, and the hook's sender must be `gitlab`. A token proves less than a signature, which is acceptable because a webhook only triggers a fetch ([ADR-0021](../adr/0021-git-sync-and-deploy-webhooks.md)).
2. **Draft and ask stays the default.** The webhook form offers deploy on push as one step with a step-up, and says what it means.
3. **Hooks belong to a remote and branch, not to a stack.** One hook triggers every sync that follows it, and the node keeps one cache per remote and branch. A single fetch fanned out to every stack can follow in v0.3.x.
4. **The mirror is on the backlog**, not in v0.3 or v0.3.x. People who sync from git already keep their source there, and backups are a non-goal. The `stacks.mirror` grant and the `stack.mirror.push` verb aren't added until it comes back.

Settled by the maintainer on 2026-10-29 (remote nodes and fleet stacks), each as recommended:

5. **Join tokens from any address.** Pairing is limited to private addresses because the secret approves at once; a join token only makes a pending node, and an admin approves it after comparing the fingerprint. A VPS reaching the hub over the internet then works without widening `CHADASH_NODE_PAIRING_FROM`.
6. **Approval needs a step-up.** Yes, `fresh`, as for T3 actions. The hub sends an approved node stack secrets when it deploys there.
7. **A Docker integration on approval, on by default.** Yes, with the box on the Add node form to turn it off.
8. **Self-update in v0.3, the node's own update later.** The hub can be recreated by its node; the node can't safely recreate itself, and needs a helper container or the Update Center.
9. **Move rewrites relative paths to absolute ones.** Yes, shown line by line in the review, so `./data` keeps meaning the same data. The alternative, refusing every relative path, would refuse most real stacks.
