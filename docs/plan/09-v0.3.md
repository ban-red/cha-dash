## Git sync and deploy webhooks

### How a sync runs

1. **Trigger.** The poll timer fires (default every 5 minutes, at least 1, with jitter), or a valid webhook arrives. Triggers coalesce: one sync per stack at a time, and at most one more queued behind it.
2. **Check.** The hub calls `stack.remote.check` on the stack's node. The node lists the remote's refs without fetching. If the tip is the last SHA seen, the sync stops here.
3. **Fetch.** `stack.fetch` does a shallow, single-branch fetch (depth 1) into the node's cache and returns the file at the configured path, the tip SHA, and the commit's subject and author. The cache lives in the node's state directory, not under the stacks root. Limits: 60 s per fetch, 1 MiB per file.
4. **Gate.** The hub refuses the new tip and says why in the Inbox when:
   - its SHA is the rejected SHA;
   - the sync is held or paused;
   - the stack has drift on disk;
   - its owner can't act any more.
   Otherwise the content becomes the stack's draft, with `source = git:<sha>`.
5. **Plan.** The hub plans `stack.deploy` as the sync's actor. An unchanged plan only records the SHA as seen.
6. **Run or ask.**
   - **Deploy on push:** approve and run.
   - **Draft and ask:** submit to the approvals flow, so the Inbox shows the plan and the commit.
   - A newer tip withdraws an older pending approval.
   - An expired approval leaves the draft in place, deployable by hand.
   - The sync always asks when the content references a stack secret outside its allowlist.
7. **Result.**
   - **Deployed:** records `last_deployed_sha`.
   - **Rolled back:** sets `rejected_sha` to that tip, and the Inbox says "Commit `abc1234` failed its health gate; `def5678` is still running."
   - **Stuck:** the same as today.

### Rules

- **Who it acts as.** A sync belongs to the admin who set it up (`owner_id`), and runs as actor kind `sync` with ID `sync:<id>` and that user's current role.
  - Losing admin, being disabled or deleting the user pauses every sync they own.
  - An admin can take a sync over. Taking it over makes it theirs and needs a step-up.
- **Editing.** A synced stack's editor is read-only and says "Edit `<path>` on `<branch>` in `<remote>`".
- **Rolling back.** A rollback from the web holds the sync at that commit until an admin resumes it.
- **Unfollowing.** Unfollow keeps the files and the history; the stack becomes a normal owned stack again.
- **Protected stacks.** Cha Dash's own stack, and any stack the node protects, can't follow git.
- **Sharing a remote.** One remote URL and branch may feed several stacks, through different paths. A mirror can't push to a URL and branch that a sync follows.

### Webhook verification

- **The route.** `POST /api/hooks/{id}`, where `{id}` is `whk_` plus 128 random bits.
  - An unknown ID, a bad signature and a disabled sync all answer the same `401 {"error":"unauthorized"}`.
  - A valid signature answers `202`, whether or not a sync follows.
- **The body.** It is read raw through `http.MaxBytesReader`, up to 1 MiB; larger answers `413`, and the next poll catches up. Only the push's `ref` is read from it: a ref that isn't the configured branch answers `202` with `ignored`.
- **Signatures accepted**, each checked with `hmac.Equal` against the hook secret:

| Sender | Header | Signed over | Replay protection |
|---|---|---|---|
| GitHub | `X-Hub-Signature-256: sha256=<hex>` | body | delivery ID (`X-GitHub-Delivery`) seen in the last 24 h |
| Gitea | `X-Gitea-Signature: <hex>` | body | `X-Gitea-Delivery` |
| Forgejo | `X-Forgejo-Signature: <hex>` | body | `X-Forgejo-Delivery` |
| Cha Dash (CI) | `X-Chadash-Signature: sha256=<hex>`, `X-Chadash-Timestamp` | `ts + "." + body`, as in `notify.Sign` | timestamp within 5 minutes |

- **Limits.** A token bucket per hook ID and per client IP, keyed like the auth limiter (IPv6 per /64). That limiter is unexported today, so wave 11 moves it to `httpx` for both to share. Failures are counted per hook, and the first in each 10-minute window is audited.
- **The secret.** Shown once, when the hook is made or rotated. Rotating it invalidates the old secret at once.

### Contracts

**Node (`internal/stackproto`, `internal/node`)**

- **Verbs.** Both return `CodeInvalid` for a URL with userinfo and `CodeForbidden` for a host outside `stacks.remotes`.
  - `stack.remote.check {url, branch, auth}` returns `{sha, host_key?}`.
  - `stack.fetch {url, branch, path, auth, host_key?}` returns `{sha, content, subject, author}`.
- **Mirror verb (v0.3.x).** `stack.mirror.push {url, branch, auth, host_key?}` returns `{pushed, head}`. It refuses a non-fast-forward with `CodeConflict`.
- **Credentials.** `auth` is `{kind: "none"|"https"|"ssh", username?, secret?}`, filled in from the vault per call and never logged. The node scrubs it from errors.
- **Deploy source.** `DeployRequest.Source` (optional, `<url>@<sha>`) becomes a `Chadash-Source` trailer. The commit subject's `by` reads "by git sync for sam".
- **Policy.**
  - New grants: `stacks.sync` (default on) and `stacks.mirror` (default off).
  - New optional list: `stacks.remotes` (host names or `host:port`; empty means any).
  - Add `PermSync` and `PermMirror` to `stackproto`.

**Hub (`internal/stacks`, `internal/action`, `internal/authz`)**

- **Actor.** `action.ActorSync`. `authz.Decide` resolves its owner the same way it resolves a token's user. `NeedsApproval` returns true for `mode = ask`, and whenever the hub sets `RequireApproval` on the plan (the secret allowlist).
- **The syncer.** `stacks.Syncer` runs one goroutine with a ticker, plus a single-flight per sync. It starts with the hub and stops with its context.
- **Secrets.**
  - The remote credential is stored at `stacksync/<id>/credential`, and the hook secret at `stacksync/<id>/hook`.
  - These names are outside `stacks/` so they never show up in the stack secrets list.

**Migration `00015_stack_sync.sql`**

```sql
CREATE TABLE stack_syncs (
  id                TEXT PRIMARY KEY,          -- syn_…
  node              TEXT NOT NULL,
  stack             TEXT NOT NULL,
  url               TEXT NOT NULL,             -- no userinfo
  branch            TEXT NOT NULL,
  path              TEXT NOT NULL,             -- default '<stack>/compose.yaml'
  auth_kind         TEXT NOT NULL CHECK (auth_kind IN ('none','https','ssh')),
  host_key          TEXT,                      -- pinned SSH host key, when ssh
  mode              TEXT NOT NULL CHECK (mode IN ('deploy','ask')),
  poll_seconds      INTEGER NOT NULL,
  secrets_allow     TEXT NOT NULL,             -- JSON array of stack secret names
  owner_id          TEXT REFERENCES users (id) ON DELETE SET NULL,  -- NULL: owner deleted, sync paused
  hook_id           TEXT UNIQUE,               -- whk_…, NULL when no hook
  state             TEXT NOT NULL CHECK (state IN ('active','held','paused')),
  state_reason      TEXT NOT NULL,
  last_seen_sha     TEXT NOT NULL,
  last_deployed_sha TEXT NOT NULL,
  rejected_sha      TEXT NOT NULL,
  last_error        TEXT NOT NULL,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  UNIQUE (node, stack)
) STRICT;

ALTER TABLE stack_drafts ADD COLUMN source TEXT NOT NULL DEFAULT 'web';  -- 'web' | 'git:<sha>'
```

The mirror's table (`stack_mirrors`, one row per node) comes with the mirror, in its own migration.

### HTTP

| Route | Access | What |
|---|---|---|
| `GET /api/stacks/{node}/{stack}/sync` | Admin | The sync's settings and state; the hook URL, never its secret |
| `PUT /api/stacks/{node}/{stack}/sync` | Admin | Follow, or change; needs a step-up when `mode` becomes `deploy` or the URL changes |
| `DELETE /api/stacks/{node}/{stack}/sync` | Admin | Unfollow |
| `POST /api/stacks/{node}/{stack}/sync/check` | Admin | Test: reach the remote, show the tip and the SSH host key to pin |
| `POST /api/stacks/{node}/{stack}/sync/now` | Admin | Check now |
| `POST /api/stacks/{node}/{stack}/sync/resume` | Admin | Resume a held or paused sync |
| `POST /api/stacks/{node}/{stack}/sync/hook` | Admin | Make or rotate the hook; answers the secret once |
| `DELETE /api/stacks/{node}/{stack}/sync/hook` | Admin | Remove the hook |
| `POST /api/hooks/{id}` | **Signature** (new) | The webhook |

`authz.Signature` works like `NodeKey`: Guard passes the route through with no session, no person's role ever satisfies it, and the handler must verify the request. `routes_test.go` lists every `Signature` route by name, so a new one is a reviewed change.

### Audit and Inbox

- **Audit actions.**
  - Changes to a sync: `stack.sync.create`, `stack.sync.update`, `stack.sync.delete`, `stack.sync.resume` and `stack.sync.takeover`.
  - Hooks and fetches: `stack.hook.rotate`, `stack.hook.delete`, `stack.hook.refused` (rate-limited) and `stack.sync.fetch` (only when the tip is new).
  - Deploys are ordinary `stack.deploy` actions, by actor `sync:<id>`.
- **Inbox items.** Class `stack` for a rejected commit, a held or paused sync, and a fetch failing for more than 3 polls. Class `approval` for draft and ask. Notification defaults: a rejected commit is "needs attention"; a fetch failing is a hint.

### Tests

- **Node.**
  - Fetch against a local bare repo served over `file://`, with the transport tests stubbed for HTTPS and SSH.
  - The allowlist, userinfo refusal, the size and time limits, and credential scrubbing.
- **Hub.**
  - The syncer as a table of states: new tip, same tip, rejected tip, drift, held, owner demoted, newer tip during a pending approval.
  - Signature vectors for all four senders, plus wrong secret, wrong sender header, replay and stale timestamp.
  - `authz` rows, including that the `Signature` list is exact.
- **Fuzzing.** `FuzzHookVerify` on the header and body parsing.
- **Dogfood.** A test repo on a git server the maintainer picks, feeding a scratch stack on pvedocker: a good push deploys, a bad tag is blocked at preflight, and a crash-looping image rolls back and is marked rejected.

## OIDC and forward-auth

### Sign-in flow

1. **Start.** `GET /api/auth/oidc/start?return=/path` makes a row in `oidc_logins` with state, nonce, PKCE verifier and return path, then redirects to the provider. The row expires after 10 minutes, and the return path must be a same-origin path.
2. **Callback.** `GET /api/auth/oidc/callback` checks state, exchanges the code with the verifier, and verifies the ID token: issuer, audience, expiry and nonce.
3. **Look up.** The `(iss, sub)` pair is looked up in `oidc_identities`:
   - **Linked:** apply the group mapping, then `StartSession(…, "oidc")`.
   - **Not linked, provisioning on, and a mapped group present:** create the user with that role, link, start the session.
   - **Otherwise:** "This account isn't linked to a Cha Dash user. Sign in another way and link it from your settings."
4. **Link.** A signed-in user starts the same flow with `?link=1`. The callback links instead of signing in, and needs a step-up first.

### Group mapping

- The settings hold a list of `{group, role}`, with roles from admin down to household; owner isn't offered.
- On each sign-in, a linked user's role becomes the highest role their groups map to. The owner is never changed.
- For a user whose role comes from groups, the role is changed in the provider. The Users page shows "from groups" and doesn't offer the role picker.
- When no group maps, the sign-in is refused, and `auth` emits `user.changed` so open sockets close.

### Step-up

- A user with a passkey steps up with the passkey.
- A user without one is sent to the provider with `prompt=login` and `max_age=0`, and the step-up counts only if `auth_time` is under 60 s old.
- The settings page's "Test" reports whether the provider sends `auth_time`.

### Forward-auth

- **Settings.** On or off; header names (defaults `Remote-User`, `Remote-Groups`, `Remote-Email`); the same group mapping as OIDC.
- **Trust.** Headers count only when the TCP peer is in `CHADASH_TRUSTED_PROXIES`. Otherwise they are stripped before any handler sees them, and the first such request per peer and hour is audited.
- **Sessions.** A request with a valid user header and no session gets a session with method `forward_auth`, for the user linked to that username.
- If the header names a different user than the session's, the session ends.

### Contracts

**Migration `00016_oidc.sql`**

```sql
CREATE TABLE oidc_identities (
  issuer      TEXT NOT NULL,
  subject     TEXT NOT NULL,
  user_id     TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  email       TEXT NOT NULL,      -- shown in settings only, never used to match
  created_at  INTEGER NOT NULL,
  last_used_at INTEGER NOT NULL,
  PRIMARY KEY (issuer, subject)
) STRICT;

CREATE TABLE oidc_logins (
  state       TEXT PRIMARY KEY,
  nonce       TEXT NOT NULL,
  verifier    TEXT NOT NULL,
  return_to   TEXT NOT NULL,
  link_user   TEXT REFERENCES users (id) ON DELETE CASCADE,  -- set when linking
  expires_at  INTEGER NOT NULL
) STRICT;

CREATE TABLE forward_auth_links (
  username    TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  created_at  INTEGER NOT NULL
) STRICT;
```

**Settings.**
- The provider settings (issuer URL, client ID, scopes, group claim name, mappings, provisioning, hide password form) live with the security settings.
- The client secret is stored at `auth/oidc/client-secret`.
- Exports carry everything but the secret; imports of these settings are owner-only, like the rest of security.

### HTTP

| Route | Access | What |
|---|---|---|
| `GET /api/auth/oidc/start` | Public | Begin sign-in or linking |
| `GET /api/auth/oidc/callback` | Public | Finish it |
| `GET /api/settings/sign-in` | Owner | Provider, mappings, forward-auth |
| `PUT /api/settings/sign-in` | Owner | Change them; needs a step-up |
| `POST /api/settings/sign-in/test` | Owner | Discovery, a test login URL, whether `auth_time` is sent |
| `GET /api/auth/identities` | SignedIn | Your linked identities |
| `DELETE /api/auth/identities/{issuer}/{subject}` | SignedIn | Unlink one; needs a step-up |
| `GET /api/users/{id}/identities` | Admin | Someone else's, for support |

### Events and audit

- **Auth events.** A new `auth` event, `signed_in`, with its method. Every sign-in method emits it.
- **Audit actions.**
  - Sign-ins: `auth.oidc.signin`, `auth.oidc.refused` (with the reason: unlinked, no mapped group, bad token) and `auth.forward.signin`.
  - Identities: `auth.oidc.link` and `auth.oidc.unlink`.
  - Settings: `settings.sign_in.update`.

### Tests

- **Flow.** A fake provider in tests (`httptest` with discovery, JWKS and a token endpoint) covers:
  - state, nonce and PKCE mismatches;
  - a wrong audience and expiry;
  - unlinked, linking, provisioning;
  - group changes that lower a role and that remove every group;
  - an owner who is never changed;
  - step-up with and without `auth_time`.
- **Forward-auth.** Headers from an untrusted peer are stripped; a trusted peer signs in; a changed user header ends the session.
- **Routes.** `authz` rows for the new routes. The callback works without a session and never accepts a return path off the origin.

## Open questions

1. **GitLab.** It sends the secret as a plain `X-Gitlab-Token` header. Accept it with a constant-time compare (no body integrity), or leave GitLab to polling?
2. **Default mode.** Draft and ask is the safer default. Is deploy on push what most people expect when they add a webhook, so the form should suggest it?
3. **One remote, many stacks.** Should v0.3 already fetch once per remote and fan out to every stack that follows it, or wait for v0.3.x?
4. **Mirror.** Is the mirror worth doing in v0.3 at all, given that the stacks root can already be backed up with the rest of its host?
