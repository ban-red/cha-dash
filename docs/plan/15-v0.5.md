## Glance

The Front Page is built for a person at a desk. A wall tablet and a TV need a different contract: nobody touches them, they run for weeks, and they're seen from across a room.

### Wall and kiosk mode

- **A display is a board in kiosk mode:** no chrome, no edit mode, no menus. Opened at `/display/<board>` with a display token.
- **Calm by default.** Dims after a quiet period, tints warm at night (hub's local time), and moves content a few pixels every few minutes against burn-in. Rotation between boards is optional.
- **Wakes on a change:** a new incident at attention or worse brings it to full brightness and shows the one line that changed. It dims again once that's resolved or acknowledged.
- **Stale is visible.** If the WebSocket drops, the display says how old its data is, rather than looking calm.
- Browser only, no app: Fully Kiosk, a Raspberry Pi in Chromium kiosk, or a tablet's guided mode. The docs show one of each.

### TV mode

The same display route at a TV's size: type sized for 3 m, focus moved by arrow keys, no hover-only information. Every widget renders at its Simplified level.

### Levels of detail

[02 · Experience](02-experience.md#levels-of-detail) defines four levels for every widget: Full, Compact, Simplified (wall and TV) and Ink (e-ink and print). v0.5 makes them a requirement: each widget renders all four, in every state (loading, live, stale, error, empty), in every theme (eight today). Visual regression (E5) holds them there, and axe runs on each.

### Display tokens

A display has no person at it, so it can't hold a session that needs a passkey. A display token ([W2](#open-questions-w1w10)):

- reads one board and only what that board shows; it can't act, read a secret or open a resource sheet;
- is made by an admin in Settings → Displays, shown once as a link to open on the device, and revocable;
- is a third token kind beside `api` and `agent`, with its own route access, refused everywhere but the display's routes.

## Integrations

Prefer a spec unless the API needs Go (see `internal/README.md`).

### TrueNAS

TrueNAS's REST API is deprecated in favour of its WebSocket JSON-RPC API, so this is Go, Tier 0 ([W3](#open-questions-w1w10)). Read only in v0.5: pools and their health, datasets and usage, disks and SMART, apps, replication and snapshot tasks. A degraded pool or a failed replication is an incident; replication tasks feed backup coverage like PBS does. Check the API against the current TrueNAS release and a test instance before the wave.

### Home Assistant both ways

v0.2 reads Home Assistant. v0.5 lets HA read Cha Dash: the home's health, open incidents and updates waiting as HA entities, so an automation can flash a light when something breaks. How it gets there is [W4](#open-questions-w1w10). Proposing a Cha Dash action from HA waits for v0.5.x: it would go through the same approval as an agent's proposal.

### Network and power

| Source | Why it needs | Tier |
|---|---|---|
| UniFi | Devices, clients and WAN health; a session login | Go |
| Tailscale | Devices, last seen, key expiry; an API key | Spec |
| Cloudflare Tunnel | Tunnels and their connections; an API token | Spec |
| Technitium | DNS health and blocked counts; an API token | Spec |
| NUT | UPS status and runtime, over NUT's TCP protocol; a low battery is an incident at attention | Go |

Each ships a recipe, fixtures under `testdata/integrations/<id>/` and a contract test.

## Specs

- **`v1beta1`**: what `v1alpha1` learned, with a migration the hub runs on an installed spec, and `spec lint` naming what changed. `v1alpha1` keeps loading through v0.5.x ([W6](#open-questions-w1w10)).
- **`chadash spec new <id>`** writes a spec, a fixtures folder and a recipe to fill in, so a community spec starts from a passing `spec test`.
- The community repository moves its specs to `v1beta1`.

## Toward 1.0

v1.0 promises stable config, API and spec formats. v0.5 makes them checkable, without promising yet:

- **The config schema**, every flag and env var, published from the code like the OpenAPI document, with a version.
- **An API deprecation rule:** a route or field is marked deprecated in the OpenAPI document for at least one minor version before it goes.
- **Upgrade tests:** CI starts the current build on a data directory from 0.3.0 and 0.4.0 and checks the migrations, the vault and a sign-in.
- **E5 · Visual regression** with Vitest browser mode, baselines made only in CI.
- **E7 · SLSA Build L3:** images built in a reusable workflow, attestations pushed to the registry, `gh attestation verify` in the release notes.

## Done when

- A wall display runs a week on a real board, dims, wakes on one incident and shows its age when the hub is away.
- Every widget passes visual regression and axe at all four levels, in every theme.
- A display token can read its one board and nothing else; tests prove each refusal.
- TrueNAS, NUT and the network sources pass their contract tests, and `live:verify` finds no drift from their fixtures.
- Home Assistant shows Cha Dash's health as entities on the maintainer's HA.
- An installed `v1alpha1` spec migrates to `v1beta1` and keeps working.
- CI upgrades a 0.3.0 and a 0.4.0 data directory.
- Every open v0.4 manual test is an automated test in CI ([17](17-test-automation.md#done-when)), and no v0.5 check needs a person.
- Dockhand is off on pvedocker and its stacks are managed by Cha Dash ([16](16-stacks-parity.md#done-when)).

## Decisions

Settled by the maintainer on 2026-11-01: **W1–W10 all as recommended.**

1. **W1:** one release in seven waves; the network sources slip to v0.5.x before wall mode does.
2. **W2:** displays sign in with a display token, a third token kind: read-only, one board, revocable.
3. **W3:** TrueNAS through its WebSocket JSON-RPC API, in Go, checked against the current release first.
4. **W4:** Home Assistant reads Cha Dash through a small HA custom integration in its own repository, with an API token.
5. **W5:** UniFi, Tailscale, Cloudflare Tunnel, Technitium and NUT; OPNsense as a spec in v0.5.x; no pfSense.
6. **W6:** spec format `v1beta1` in v0.5; `v1` at 1.0.
7. **W7:** quiet hours per display; only a critical incident wakes it.
8. **W8:** acknowledged incidents show dimmed, with who's on it, and don't wake a display.
9. **W9:** release notes stay off by default.
10. **W10:** the end-to-end CI job runs with test automation on.
