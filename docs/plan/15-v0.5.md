## Glance

The Front Page is built for a person at a desk. A wall tablet and a TV need a different contract: nobody touches them, they run for weeks, and they're seen from across a room.

### Wall and kiosk mode

- **A display is a board in kiosk mode:** no chrome, no edit mode, no menus. Opened at `/display/<board>` with a display token.
- **Calm by default.** Dims after a quiet period, tints warm at night (hub's local time), and moves content a few pixels every few minutes against burn-in. Rotation between boards is optional.
- **Wakes on a change:** a new incident at attention or worse brings it to full brightness and shows the one line that changed. It dims again once that's resolved or acknowledged.
- **Stale is visible.** If the WebSocket drops, the display says how old its data is, rather than looking calm.
- Browser only, no app: Fully Kiosk, a Raspberry Pi in Chromium kiosk, or a tablet's guided mode. The docs show one of each.

### TV mode

The same display route at a TV's size: type sized for 3 m, focus moved by arrow keys, no hover-only information. Every widget renders at its Simplified level.

### Levels of detail

[02 · Experience](02-experience.md#levels-of-detail) defines four levels for every widget: Full, Compact, Simplified (wall and TV) and Ink (e-ink and print). v0.5 makes them a requirement: each widget renders all four, in every state (loading, live, stale, error, empty), in every theme (eight today). Visual regression (E5) holds them there, and axe runs on each.

### Display tokens

A display has no person at it, so it can't hold a session that needs a passkey. A display token ([W2](#open-questions-w1w10)):

- reads one board and only what that board shows; it can't act, read a secret or open a resource sheet;
- is made by an admin in Settings → Displays, shown once as a link to open on the device, and revocable;
- is a third token kind beside `api` and `agent`, with its own route access, refused everywhere but the display's routes.

## Integrations

Prefer a spec unless the API needs Go (see `internal/README.md`).

### TrueNAS

TrueNAS's REST API is deprecated in favour of its WebSocket JSON-RPC API, so this is Go, Tier 0 ([W3](#open-questions-w1w10)). Read only in v0.5: pools and their health, datasets and usage, disks and SMART, apps, replication and snapshot tasks. A degraded pool or a failed replication is an incident; replication tasks feed backup coverage like PBS does. Check the API against the current TrueNAS release and a test instance before the wave.

### Home Assistant both ways

v0.2 reads Home Assistant. v0.5 lets HA read Cha Dash: the home's health, open incidents and updates waiting as HA entities, so an automation can flash a light when something breaks. How it gets there is [W4](#open-questions-w1w10). Proposing a Cha Dash action from HA waits for v0.5.x: it would go through the same approval as an agent's proposal.

### Wave 33: how displays work

**The credential.** A display is its own row (`displays`, migration 00029), not an `api_tokens` row: an API token acts as its user with that user's role, and a display has no user and no role. Its secret is `cdd_<26 base32>_<52 base32>` (ID `dsp_<26>`), stored as SHA-256 like a token's. It names one board, has a name, optional quiet hours (`HH:MM` to `HH:MM`, the hub's local time), who made it, when it was last seen and from where, and when it was revoked and by whom.

**Signing a device in.** The link Settings → Displays shows once is `<origin>/display/<board>#<secret>`. The secret is in the fragment, so it isn't sent in the URL or logged. The page posts it to `POST /api/display/claim`, which sets an `HttpOnly`, `SameSite=Strict` cookie, `chadash_display`, with `Path=/api/display` and a 400-day lifetime, and then the page drops the fragment. The cookie is never sent to any other route. A script may send `Authorization: Bearer cdd_…` to the same routes.

**Routes.**

- Admin, session only: `GET`/`POST /api/displays` and `PATCH`/`DELETE /api/displays/{id}`.
- `DisplayToken` access, a new `authz.Access` that takes a display's credential and nothing else:
  - `GET /api/display`: the display, its board and layout, and the hub's zone;
  - `GET /api/display/ws`: the display's socket;
  - `GET /api/display/icons/{id}`: icons for its tiles.
- A display's credential counts for nothing anywhere else. The cookie isn't sent there, and `Bearer cdd_` isn't an API token, so those routes answer 401.

**What it reads.** The socket serves `graph`, `metrics`, `inbox`, `causes` and `backups`, never `tasks`.

- The inbox is household's projection of the incidents that `boards.BoardScope` of the display's board shows, and the backups follow the same scope. A board whose scope is All (never saved, or it has the Incidents widget) gets household's whole view.
- The graph, its causes and the metrics are household's view, not scoped. A tile's widget reads neighbours that a board's items don't name, which is why household's graph isn't scoped either. Scoping them waits for lenses.
- A revoked display's sockets close at once, and every socket rechecks each minute.

**Calm (web, `lib/display.ts`, a pure function of the time, the incidents, the connection and the display's settings):**

- Full brightness for 2 minutes after a change, then it dims.
- Warm tint from 21:00 to 07:00 hub time.
- In quiet hours it goes dark, and only an unacknowledged `down` incident wakes it.
- An unacknowledged incident at `attention` or `down` that's new since the page saw it wakes the display and shows its one line. It dims again once the incident is resolved or acknowledged. Acknowledged incidents show dimmed, with who's on them, and don't wake it.
- The content moves a few pixels every 3 minutes against burn-in.
- When the socket is down, the display shows how old its data is.

**Not in 33.**

- Rotation between boards: a display reads one board (W2). Rotation would need a display to name several boards, and that's its own decision.
- Camera pictures: the picture route stays signed-in only, so a camera tile on a display shows its placeholder.
- TV mode and the detail levels are wave 34.

### Wave 34: levels, TV and e-ink

- **Levels** (`web/src/lib/level.ts`). The surface picks the level, not the widget:
  - full at a desk;
  - compact at the phone breakpoint;
  - simplified on a wall or TV display;
  - ink on an e-ink display, and when a board is printed.

  `Tile` marks itself, and `styles/tiles.css` builds each level from the parts every widget already uses (`.v`, `.sub`, `.kv`, `.tf`, `.list`; `data-control` for controls). One set of rules gives all 27 widgets their four levels without 108 hand-made layouts. A widget that needs its own treatment at a level adds it beside its other sizes. At ink, `ago()` is absolute.
- **Display styles** (00030): wall, TV or ink.
  - **TV:** the board at 1.5× zoom. A remote's arrow keys move focus between tiles (`lib/spatial.ts`: the nearest box that way, straight ahead first). The focused tile shows what simplified hides, so nothing is hover-only.
  - **Ink:** never dimmed, tinted or moved.
- **Tests:**
  - axe on every widget at every level, in each state, at its smallest and largest sizes (`test/a11y-levels-*.test.ts`);
  - unit tests for the levels, spatial focus and the three styles on the display page;
  - visual regression (E5, `test/visual/`): one sheet per widget and theme, levels by states, with baselines made in CI.

**34, as built (2026-11-06).** Still open from 34:

- Printing a board keeps relative times: print CSS can't change text, and an ink level for print would need a print route.
- The TV's 1.5× zoom is one size for every TV, rather than one sized from the viewport.

- A wall display runs a week on a real board, dims, wakes on one incident and shows its age when the hub is away.

- A display token can read its one board and nothing else; tests prove each refusal.

## Decisions

Settled by the maintainer on 2026-11-01: **W1–W10 all as recommended.**

1. **W1:** one release in seven waves; the network sources slip to v0.5.x before wall mode does.
2. **W2:** displays sign in with a display token, a third token kind: read-only, one board, revocable.
3. **W3:** TrueNAS through its WebSocket JSON-RPC API, in Go, checked against the current release first.
4. **W4:** Home Assistant reads Cha Dash through a small HA custom integration in its own repository, with an API token.
5. **W5:** UniFi, Tailscale, Cloudflare Tunnel, Technitium and NUT; OPNsense as a spec in v0.5.x; no pfSense.
6. **W6:** spec format `v1beta1` in v0.5; `v1` at 1.0.
7. **W7:** quiet hours per display; only a critical incident wakes it.
8. **W8:** acknowledged incidents show dimmed, with who's on it, and don't wake a display.
9. **W9:** release notes stay off by default.
10. **W10:** the end-to-end CI job runs with test automation on.
