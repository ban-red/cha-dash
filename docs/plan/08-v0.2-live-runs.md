## Why by hand, through the web

The Done-when is about what a person sees: undo for T1, the hold ring and blast radius for T2, a typed name and step-up for T3, a stack that rolls back on its own. A Go test can check the engine, and CI already does. It can't check the ladder in a browser against a real daemon. So the maintainer runs this checklist in the web, and checks the shell for what the web can't show. A `write` mode for `spikes/live-verify` can follow for the API-only platforms.

## The target

**Only the node sandbox:** CT 3696 on mars-2, made by [`spikes/node-sandbox/sandbox.sh`](../../spikes/node-sandbox/README.md). It's unprivileged Docker in an LXC, like pvedocker, and nothing depends on it.

The sandbox runs the **shipped `deploy/compose.yaml`**, hub and node together. That makes the CT "the hub's host" of the Done-when: the hub has no socket and the node does every write. The dev hub on the Mac and its `data/` take no part.

| Named target | What | Used by |
|---|---|---|
| `throwaway` | `nginx:1.27-alpine` with a healthcheck, `--restart unless-stopped`, one named and one anonymous volume, started from the shell | B |
| `hello` | The sample project `sandbox.sh` starts at `/opt/stacks/hello` | C1 |
| `scratch` | A stack Cha Dash creates: `web` (nginx with a healthcheck) and `app` (`depends_on: web`) | B2, C2–C11 |

**Out of bounds:** every other host. Remote nodes are v0.3, so there's no path to pvedocker or jupiter anyway; keep it that way by not adding any other Docker instance to this hub.

## Prepare

1. **A fresh CT**, so the starting state is known: `sandbox.sh destroy`, then `create`.
2. **Images from one commit.** The maintainer builds the hub (default target) and the node (`--target node`) for linux/amd64 from a clean checkout, tags them `live-<short sha>`, and loads them into the CT (`docker save … | ssh … docker load`). Write the SHA down; every result belongs to it.
3. **Copy `deploy/compose.yaml`** to `/root/chadash/` in the CT, with a `compose.override.yaml` that sets both images to the `live-<sha>` tags.
4. **Record the versions:** commit, Docker Engine, Compose plugin, containerd, kernel, PVE.
5. **Open the hub through a tunnel**, `ssh -L 3696:localhost:3696 root@<sandbox>`, and browse to `http://localhost:3696`. Passkeys need a secure context, and localhost is one, so step-up works without TLS.
6. **Accounts:** the owner, with a passkey; an Operator; a Viewer. Each in its own browser profile.
7. **Evidence folder** on the Mac: `~/.local/share/chadash-spikes/live-runs/<date>/` (0700). Screenshots, task logs and command output go there, never into the repo.

**Rules while running.** Stop at the first result that differs from *Expect*, write it down with the task ID, and fix before going on. Nothing in this run needs `.env.local`.

## E · The node's idle RSS

The budget is ≤ 40 MB idle RSS and a ≤ 40 MB binary ([08 · v0.2](08-v0.2.md), ADR-0016, ADR-0020). Spike 4.6 measured about 35 MB per command; `spikes/footprint/node` measures a long-running node with no daemon. This is the missing number: a long-running node against a real daemon.

1. After A–D, close every browser tab and leave the CT alone for 30 minutes (**idle**).
2. Then keep one board open, so the Docker event stream runs, for 30 minutes (**watched**).
3. Sample every 60 s, in the CT:

   ```bash
   while sleep 60; do printf '%s %s %s\n' "$(date +%s)" "$(ps -o rss= -p "$(pgrep -x chadash-node)")" "$(docker stats --no-stream --format '{{.MemUsage}}' chadash-chadash-node-1)"; done | tee node-rss.txt
   ```

   The first figure is RSS in KiB; the second is the cgroup's view (with page cache) against the 128 MB cap.
4. Also record the peak during C2's deploy (`/proc/<pid>/status`, `VmHWM`) and the binary's size in the image.
5. Report min, median and max for each phase. Over 40 MB idle means either a fix or a revised budget with its reason, in ADR-0016's consequences.

## PBS · prune per policy

`pbs.datastore.prune` was built against a synthetic PBS ([integrations/pbs](../../integrations/pbs/README.md#actions)). This run checks it on a real one, on a **scratch datastore only**: a prune deletes snapshots, and DatastoreAdmin can read and delete every backup on its datastore.

**Target.** Datastore `chadash-scratch` on the lab's PBS, holding six throwaway backups of a one-file folder in one group (`host/chadash-scratch`, written from a PVE host with the control token, so the control token owns it; the lab's PBS is a container with no `proxmox-backup-client`, and `root@pam` gets "permission check failed" there), with a **disabled** prune job `chadash-scratch-prune` that keeps the last 2. Disabled, so PBS never prunes it on its own schedule and the Inbox's filling incident would suggest the action.

**Tokens**, each on its own user, so teardown is three `user delete`s:
- `chadash-test@pbs!read`: Audit on `/` (the read recipe);
- `chadash-control@pbs!control`: DatastoreAdmin on `/datastore/chadash-scratch` (the control recipe);
- `chadash-weak@pbs!weak`: DatastorePowerUser on the same datastore, for P4 only.

The maintainer creates the datastore, backups, job, users and tokens, and enters the secrets in Cha Dash. Claude plans and, with the maintainer's go-ahead for each, approves.
