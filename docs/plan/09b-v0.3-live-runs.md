## Why by hand

The same reason as [08b](08-v0.2-live-runs.md#why-by-hand-through-the-web). Go tests cover the engine, the signatures and the token checks against fakes. They can't cover:
- a real git server's webhook;
- a real identity provider's tokens;
- a node joining over the network from another host;
- the hub's own container being replaced under it.

## Prepare

1. **Fresh CTs:** `sandbox.sh destroy` and `create` for both A and B.
2. **Images from one commit.**
   - Build them in Sandbox A from `git archive <sha>`, which holds only committed files, so no `.env.local` and no `data*/`. Use `docker build` for the hub and `docker build --target node` for the node, tag both `live-<short sha>`, and pass `VERSION` and `COMMIT`. It's native amd64, so there's no cross-build.
   - Copy the node image to Sandbox B (`docker save … | ssh … docker load`).
   - Write down the SHA.
   - For J, the hub must run a **ghcr** tag with a registry digest: self-update refuses a hub built or loaded locally. Run J on its own after F–I, with `<good>` as the starting image.
3. **Sandbox A:** run `deploy/compose.yaml` with a `compose.override.yaml` for the `live-<sha>` tags. Set:
   - `CHADASH_PUBLIC_URL` to the address B and the git server will use;
   - `CHADASH_TRUSTED_PROXIES` to the test proxy, for H5–H8 only;
   - `CHADASH_NODE_SELFUPDATE: "true"`, which the shipped file already has.
4. **Forgejo, Pocket ID and Caddy on Sandbox A**, in their own compose project, `testkit`, beside Cha Dash's. Nothing in the lab changes, and `sandbox.sh destroy` removes all of it.
   - **Names.** On the Mac, map `id.sandbox.test` and `git.sandbox.test` to Sandbox A's address in `/etc/hosts`. In the hub's `compose.override.yaml`, add the same two names with `extra_hosts`.
   - **The CA.** Import Caddy's root certificate into each test browser profile. Give the hub a bundle with it too: the system bundle plus Caddy's root, mounted read-only, with `SSL_CERT_FILE` pointing at it.
   - **Pocket ID:**
     - Set it up through `https://id.sandbox.test`.
     - The client's redirect URI is the one Settings → Sign-in shows.
     - Make the group and the test user, and register the user's passkey in their own browser profile.
   - **Forgejo:**
     - It serves at `http://git.sandbox.test:3000`, with plain HTTP to test the https-over-http refusal, and through Caddy at `https://git.sandbox.test` for the syncs.
     - Make the `scratch` repository and a read-only token.
     - Allow webhooks to the hub's address: Forgejo refuses private addresses unless `[webhook] ALLOWED_HOST_LIST` names them.
5. **Record the versions:** the commit, and Docker, Compose, the kernel and PVE on both CTs. Also Forgejo, Pocket ID and Caddy, with their versions.
6. **Accounts:** the owner with a passkey, an Admin, an Operator and a Viewer, each in its own browser profile. The owner sets step-up to "passkey only" for H3.
7. **Evidence folder:** `~/.local/share/chadash-spikes/live-runs/<date>/` (0700), as in 08b. No credential, token, secret or join token goes into the repo or into this file.

**Rules while running.** Stop at the first result that differs from *Expect*. Write it down with the task or audit ID, and fix it before going on.

## L · Dogfood: the Done-when

Only after F–K pass, with a separate go-ahead naming pvedocker and the stack to move.

1. pvedocker's node joins with a join token, and is approved with a step-up.
2. A push to the stacks repo redeploys a scratch stack on pvedocker through the webhook. A bad commit rolls back and is marked rejected.
3. The owner signs in through the lab's provider, and a second account gets its role from a group.

The lab has no git server or identity provider today. Items 2 and 3 run once Forgejo and Pocket ID are installed in the lab, or against the sandbox's `testkit` if the maintainer decides they stay there. That is a separate decision from these runs.
4. One Dockhand stack moves into pvedocker's root with no container restarted, and its next deploy goes through the gate.
5. Cha Dash updates itself on the hub's host, and a bad image rolls back.

**Smaller findings, fixed after the run:** Settings → Nodes didn't show a node joining or approved elsewhere until a reload; it now reads again every five seconds while something waits. The Users page said "never signed in" after a sign-out; accounts now keep when they were last seen (`00021`). A sync skipping a rejected commit left no trace; it now audits `stack.sync.skip` once. Approving a node that re-joined under the same name reuses its Docker connection, by design.

**Corrections to this checklist**, for the next run:
- **G9:** binding the Docker socket is always refused by the node's guard, so it never reaches an approval. Use `privileged: true`, which the default policy allows but flags as root-equivalent.
- **H4:** `users.role.from_groups` is written only when the role changes. It appears after the Admin lowers the role, at the next provider sign-in.
- **H5–H8:** the test proxy was a Caddy site on the hub's Docker network, with `CHADASH_TRUSTED_PROXIES` set to its address only. To reach the passkey's origin, the browser went through an ssh forward to `localhost`.
- **I:** mount the project's directory into the node first, or it says it can't see the file.
